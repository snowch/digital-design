explanation: How a run ends tells you where to look. The debugger says one of these:

- **The program ran `stop`.** The run finished. Check what it left against what it should.
- **The debugger cut the run off.** A loop never ends, or a return address was lost, as in lesson 4.
- **The debugger paused: a register nothing has set.** A start is missing, such as `R14 <= 0x7C0`, or a line names the wrong register.
- **Cause `21`, not an instruction.** The run went past the program's end into data or 0s: a missing `stop`, or a branch to the wrong name.
- **Cause `31`, no memory at the address.** An address register went too far: a list walked past its end, or more pops than pushes.
- **Cause `33`, a word's address not a multiple of 8.** An address stepped by 4 where a word needs 8.
- **Cause `34`, a store to the ROM or a sensor.** A stack started in the wrong place, or a store to the log, which is in the ROM.

The instruction that halts is rarely the one that is wrong. Find which earlier line set the value it used.

generalisation: A mistake hides until a test reaches it. The count one short was right on two logs of five.

Fix one mistake at a time, and run every test again after each. A mended halt can uncover a second mistake behind it.

modelVsReality: The course's debugger can step back, because it keeps the states of the model. Most debuggers for real machines cannot; some record a run so it can be replayed.

On a real machine, a mistake like the stack started at `400` would write over the memory below it without a halt, and fail later, far from the line that is wrong. The course's machine halts at the first store to the ROM.
