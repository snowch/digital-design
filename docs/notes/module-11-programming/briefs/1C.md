# Brief 1C: lesson `assembly` (Module 11, lesson 1), third part

Read `00-module.md` (the shared fact sheet) first; it applies here. This lesson introduces
**assembly**, **assembler** and **debugger**; all three may appear (not in bold: they were
introduced earlier on the page). No later term (breakpoint, function, argument, calling
convention, stack, frame, recursion) may appear.

Keys to write: `explanation`, `dataLead`, `generalisation`, `beAssemblerLead`, `c2Task`,
`c2Hints` (five), `reflection`, `modelVsReality`.

## explanation (about 150 words, a numbered list allowed)

The assembler reads the program twice.

1. The first time, it gives every line its address. The first instruction is at `000`, and each
   instruction is 4 bytes after the one before. A `word` of data is 8 bytes and starts at a
   multiple of 8, so the assembler puts 0s before it where needed. Each name takes the address of
   its line.
2. The second time, it makes each word. It reads the line's transfer for the kind and the job,
   and the registers for A, B and Y.
3. A name used as an address becomes the constant: `word[limit]` loads from the address `limit`
   names.
4. A name a branch goes to becomes a count: the target's address minus the branch's, divided by 4.
5. A name may be used before the line that defines it, because the first reading has found every
   address before the second makes any word.
6. A line it cannot read, or a number that does not fit, is refused with the line's number.

## dataLead (about 60 words, above a listing figure)

1. This version keeps room A's limit as data after the program: `limit: word -180`.
2. The last instruction, `stop`, is at `018`, so the next free byte is `01C`.
3. `01C` is not a multiple of 8, so the assembler puts 4 bytes of 0s there and the word starts at
   `020`. `limit` names `020`.
4. The load `R3 <= word[limit]` becomes `38003020`: kind 3, job 8 (a word at an address the
   constant gives), Y is R3, and the constant `020`.

## generalisation (about 110 words)

1. The assembler translates line for word. It adds no instruction of its own: every word in the
   listing comes from one line you wrote.
2. You write where a branch goes; the assembler works out how far. Insert a line and every
   constant that crosses it changes, and the assembler works each one out again.
3. The text is for people: names, comments, the transfer written out. The words are for the
   machine, which never sees the text.
4. The assembler checks the form of each line. Whether the program does what you meant is a
   question for a run, and the debugger shows you the run.

## c2Task (about 90 words, with the program as a fenced code block)

1. Be the assembler for this program:

```
       R1 <= word[limit]
       R2 <= word[sensorB]
       if R2 < R1 signed goto cold
       R3 <= 1
       word[lamps] <= R3
cold:  stop
limit: word -200
```

2. Give four answers: the address `cold` names; the address `limit` names; the word of the branch
   `if R2 < R1 signed goto cold`; and the word of the load `R1 <= word[limit]`.
3. Write addresses as three hexadecimal digits and words as eight.
4. There are 4 tests, one for each answer.

## c2Hints (five, in this order)

1. The idea: give every line its address first, then make each word.
2. A common mistake: padding a word that already starts at a multiple of 8. Only a word that would
   start off a multiple of 8 gets 0s before it.
3. A smaller example: in the colder-room program, `show` is the fifth instruction, at `010`, and
   the branch at `008` gets the constant `002`.
4. Part of the answer: `cold` is the sixth instruction, at `014`, and `limit` is at `018`, a
   multiple of 8.
5. The whole answer: `cold` is `014`, `limit` is `018`, the branch is `56210003` and the load is
   `38001018`.

## reflection (about 70 words)

1. Each program so far reads one or two readings and decides once.
2. The shop keeps a log: a reading every hour, kept as words in memory, one after another.
3. A program that answers a question about the whole log must read every reading, without one
   line for each.
4. End on the question: how does a program work through a list of readings kept in memory?

## modelVsReality (about 110 words)

1. The debugger runs the instruction set, one instruction at a time, on a model. It shows no edges.
   A debugger for a real machine sits on the circuit itself: it stops the clock, or sets the
   machine to stop at an address, and reads the registers out.
2. A register nothing has set holds X in the model. Before an instruction whose address, branch or
   jump needs such a register, the debugger pauses and names it. A real machine would use whatever
   its flip-flops happen to hold.
3. A run that has not stopped after 5000 instructions is cut off, since a program may never stop.
   A real machine runs on until it is switched off.
