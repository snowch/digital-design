## explanation (about 200 words: one sentence, a list, one closing sentence)

How a run ends tells you where to look. Each item: a bold lead-in naming the end, then where to
look. Keep these facts:

- **The program ran `stop`.** The run finished. Check what it left against what it should.
- **The debugger cut the run off** after 5000 instructions. A loop never ends, or a return address
  was lost, as in lesson 4.
- **The debugger ended the run: a register nothing has set.** A start is missing, such as
  `R14 <= 0x7C0`; a line names the wrong register; or a list walked past its end into RAM nothing
  has written, whose words are not set (lesson 6's counting program, with the wrong `R2 <= R2 - 1`
  deleted, walks off an empty log this way).
- **Cause `11`, an instruction's address outside the ROM.** A `goto R15` with a word in R15 that is
  not an address in the ROM, such as a reading or a stack address.
- **Cause `12`, an instruction's address in the ROM but not a multiple of 4.** A `goto R15` with the
  wrong word in R15, as when pops run in the wrong order (lesson 4).
- **Cause `21`, not an instruction.** The run went past the program's end into data or 0s: a missing
  `stop`, or a branch to the wrong name.
- **Cause `31`, no memory at the address.** An address register went past the memory: a loop of
  pops that takes R14 up past `7C0` through the devices, or a list walked backwards past its first
  reading.
- **Cause `33`, a word's address not a multiple of 8.** An address stepped by a number that is not a
  multiple of 8.
- **Cause `34`, a store to the ROM or a sensor.** A stack started in the wrong place, or a store to
  the log, which is in the ROM, as in the failure experiment.

The instruction that halts is rarely the one that is wrong: find which earlier line set the value
it used.

## generalisation (about 90 words)

1. A mistake hides until a test reaches it. The counting program's mistake was right on two logs of
   five.
2. So test on logs chosen to reach the edges: an empty log; one reading; a log whose first or last
   reading is the one that changes the answer; a reading equal to the limit; readings of both signs.
3. Mend one mistake at a time, and run every test again after each. A mended halt can uncover a
   second mistake behind it.
4. The method does not depend on the program: what each part should leave, a pause before it, and
   the first value that differs.

## edgeTask (about 60 words)

1. Four logs, each with the limit -180: -190 and -185; -170, -175 and -160; -180 and -190; and an
   empty log.
2. Which one log would show the mistake, by making the program show a wrong number? There is 1
   test.

## edgeHints (five, in this order, each starting with its label)

1. The idea: a mistake shows only on a log whose right answer differs from the program's.
2. A common mistake: choosing a long log. Length does not matter here; the reading's value does.
3. A smaller example: a log of one reading, -150, is warmer either way, so both programs count it.
4. Part of the answer: the program and a right one differ only on a reading equal to the limit.
5. The whole answer: -180 and -190. The program shows 1, where 0 is right.

## c2Task (about 110 words)

1. The starting text counts the log's readings above the limit with the function `overBy` from
   lesson 3: for each reading it calls `overBy`, and counts the reading when the result is not 0.
2. It keeps the list's address in R10, the readings left in R11, the limit in R12 and the number of
   readings above the limit in R13.
3. It has two mistakes. Find and mend both. `overBy` is right: do not change it.
4. The tests add `count`, `limit` and `log` after your program, all with the limit -180. "Run with"
   lists the 6 logs, among them an empty log and a log with a reading equal to the limit. Each test
   checks the display and that the program ends at its `stop`.

## c2Hints (five, in this order, each starting with its label; they must hold whichever mistake the
learner mends first)

1. The idea: run, read how the run ends, find the line, mend it. Then run every log again: one
   mistake can hide the other.
2. A common mistake: stopping once the program reaches its `stop`. With one mistake mended, the
   other can still give a wrong number, or a halt on some logs.
3. A smaller example: the readings are words, 8 bytes apart, so an address that walks them goes up
   by 8 each time round.
4. Part of the answer: on log -190, -181, -175, -170 the first run halts with cause `33` at `018`,
   the load, with R10 at `074`. A breakpoint on `next` shows, at its first pause, R11 holding 96,
   which is `060`, the address of `count`, where the log has 4 readings.
5. The whole answer: change `R10 <= R10 + 4` to `R10 <= R10 + 8`, and `R11 <= count` to
   `R11 <= word[count]`.

## modelVsReality (about 60 words)

1. The course's debugger can step back, because it keeps the states of the model. Most debuggers for
   real machines cannot; some record a run so it can be replayed.
2. Real programmers choose test inputs at the edges in the same way, and keep the ones that once
   found a mistake, so the mistake cannot come back unseen.
3. Do not mention stacks, the ROM or cause `34`.
