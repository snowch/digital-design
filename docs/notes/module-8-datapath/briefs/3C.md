# Brief 3C: lesson `fetch` (Module 8, lesson 3), the end

Read `00-module.md` (the shared fact sheet) first; it applies here, with one change: PC,
"program counter" and "fetch" are allowed, used plainly (earlier sections introduced them).

Keys to write: `writeChecksLead`, `c2Task`, `c2Hints.1` to `c2Hints.5`, `reflection`,
`modelVsReality`.

## writeChecksLead (one sentence)

Write the checks the ROM makes on every fetch, as a module.

## c2Task (about 130 words, a list allowed)

1. Write a module called `checks`. Input: PC, 64 bits. Output: CAUSEF, 8 bits.
2. CAUSEF is `11` (hexadecimal) when any of PC's bits 63 to 10 is 1: PC is outside the ROM.
   Otherwise it is `12` when PC's bits 1 and 0 are not both 0: PC is not a multiple of 4.
   Otherwise it is `00`.
3. The starting text sets CAUSEF to `00` always. Replace it.
4. You may use `module`, ports, `logic`, multi-bit signals, `assign`, selects, `always_comb`,
   `if`, and the comparisons `==` and `!=`.
5. In an `always_comb` block, a later assignment replaces an earlier one.
6. There are 9 tests, each named by PC in hexadecimal: inside the ROM at multiples of 4 and not,
   at `400` and above, and the largest multiple of 4 a 64-bit word holds.

## c2Hints (five rungs)

1. Start CAUSEF at `00`, then let each check that fails replace it.
2. A common mistake: the checks in the wrong order. The outside check must win, so it comes last.
3. `if (PC[1:0] != 2'b00) CAUSEF = 8'h12;` is the multiple-of-4 check.
4. The outside check compares bits 63 to 10, which are 54 bits, with 0: `PC[63:10] != 54'h0`.
5. The whole answer: replace `assign CAUSEF = 8'h00;` with

```
always_comb begin
  CAUSEF = 8'h00;
  if (PC[1:0] != 2'b00) CAUSEF = 8'h12;
  if (PC[63:10] != 54'h0) CAUSEF = 8'h11;
end
```

## reflection (about 100 words)

1. The machine now runs a program on its own. PC names the next instruction, the ROM gives it on
   IR, the decoder sets the control signals, and the stop logic stops the machine at `stop` or at
   anything it cannot run.
2. Every instruction still works on registers and constants alone.
3. The shop's readings are at the sensors' addresses, and the display shows what is written at
   its own address (Module 6).
4. End on the question: how does an instruction read a word at an address, or write one?

## modelVsReality (about 110 words)

1. Here every instruction takes one edge: fetch and all its work fit between two edges. So the
   clock must wait for the slowest instruction's whole path: PC, the ROM, the decoder, the
   register file, the ALU and back. Module 9 splits an instruction over several edges.
2. The simulator stops the clock when the machine stops, and shows why. A real machine has no one
   to show; Module 12 lets a program say what happens instead.
3. The model's ROM gives its word as soon as PC settles. A real ROM takes time to read.
