# Brief 4C: lesson `final-machine` (Module 13, lesson 4), third part

Read `00-module.md` (the shared fact sheet) and `4-shared.md` (this lesson's facts) first; both
apply. You may use CPU, machine code, abstraction, join and trace. Call the learner's text "your
text" and the machine it describes "your machine". Call the parts the course supplies "the
course's parts".

Keys to write: `explanation`, `generalisation`, `labLead`, `c1Task`, `c1Hints.1` to `c1Hints.5`,
`reflection`, `modelVsReality`.

## explanation (about 200 words)

1. The comparison after every instruction and every trap finds a wrong join at the first
   instruction its effect reaches. It does not wait for the end of the program.
2. A wrong join shows only where a program reaches it. The timer's count is wrong only on an edge
   that traps while the timer runs; a branch's condition only where a branch is not taken; the
   door only where the door opens.
3. So each of the five programs reaches a different part: the shop's program the two instructions
   you added and a system call; user mode's refusal; the timer and a system call; the door; a
   store with no handler.
4. What the sentence names points at a part (a list):
   - the PC: the next PC's choice, or a trap or `resume` that set it;
   - a register: the word register Y takes, or the register file's write;
   - the timer or "waiting": the memory's events, and what the memory takes in;
   - a halt where the model goes on, or the reverse: the trap logic, and what it takes in.

## generalisation (about 150 words)

1. Teams that design a CPU check it this way: the same programs run on the design and on a model
   that works out each instruction in numbers, and the two are compared after every instruction.
2. They run many more programs than five, many of them made at random, and they measure which parts
   of the design the programs reached.
3. Programs that agree do not prove a design right. They show that no program reached a wrong
   part. "DOOR held at 0" passes four of the five programs.
4. The fix is a program that reaches the part, as the door program reaches the door.

## labLead (one sentence, above the challenge)

Write the whole machine's top module; the three buttons above the text give three ways in.

## c1Task (about 160 words; a short list allowed)

1. Write the top module `machine` of the whole machine. Its ports are given and stay as they are
   (list them as `4-shared.md` gives them).
2. The course's nine parts are modules you place by name: name them, as `4-shared.md` lists them.
3. Your text joins them and writes the small parts between them.
4. The three ways in, one line each, as `4-shared.md` gives them.
5. The tests: the five programs, each run on your machine and on the model, compared after every
   instruction and every trap. Name what is compared. A failed test names the first line after
   which they disagree, and what differs.

## c1Hints.1 to c1Hints.5 (each one to three sentences; the later hints say more)

1. Start from the outline. Run the tests first: each failure is a program that reaches one of the
   six `JOIN:` lines.
2. Read a failure for the value it names, then ask which part makes that value. A PC that differs
   after a trap points at the next PC's choice; a wrong timer or "waiting" points at the memory.
3. The trap logic decides, at every edge, whether to trap. It needs to know the events waiting in
   the memory and whether a handler is set; the control registers know the second.
4. User mode is C0's bit 0 turned over: bit 0 is 1 in system mode. The control registers give C0
   as STATUS. The control registers take the cause of a trap for C3 from the trap logic.
5. Set if writes MET, the branch condition, as a whole word, 0 or 1, when SET is 1. A trap's edge
   gives the PC the handler's address, which the control registers give as C4.

## reflection (about 80 words)

1. You joined the course's parts into the whole machine, and five programs ran on it as on the
   model.
2. Ask yourself: which failure sentence led you to which join, and which join took longest to
   find?
3. Next: a program of your own runs on the whole machine, and you trace it down to the gates.

## modelVsReality (about 120 words)

1. The course's comparison runs the model and your machine side by side, in the same browser.
2. Real teams that design a CPU do the same, at far greater scale: the model is a program that
   runs each instruction in numbers, and the design runs in a simulator of its gates or of its
   text, and the two are compared after every instruction.
3. Their tests run millions of instructions, many from programs made at random.
4. Some checks are proofs about the design for every input rather than tests of chosen programs.
   The course does not teach them.
