# Brief 4B: lesson `final-machine` (Module 13, lesson 4), second part

Read `00-module.md` (the shared fact sheet) and `4-shared.md` (this lesson's facts) first; both
apply. You may use CPU, machine code, abstraction, join and trace. Call the learner's text "your
text" and the machine it describes "your machine". Call the parts the course supplies "the
course's parts".

Keys to write: `investigation`, `invLead`, `invAfter`, `construction`, `failureExperiment`,
`failLead`, `failAfter`.

## investigation (about 90 words, above the figure)

1. The figure has three texts, each the course's text with one line changed: "Every branch taken",
   "Interrupts on in system mode" and "A call keeps the PC". It has all five programs.
2. Each changed line is wrong. The question is which programs find it.
3. Say in one sentence what each line should do, from `4-shared.md`: a branch goes to its target
   only when MET holds; IE is C0's bit 1; a call writes the PC plus 4.

## invLead (one sentence)

Run each text on each program, and note which programs disagree with the model.

## invAfter (about 120 words, below the figure)

1. "Every branch taken": only the timer program disagrees, at `if R5 == R6 goto back` at `038`.
   The other four have no branch.
2. "Interrupts on in system mode": the timer program and the door program disagree; the door
   program's machine halts with cause `82` at `R5 <= C3`, the handler's first instruction, which
   traps again.
3. "A call keeps the PC": only the shop's program disagrees, at `call R6, R15`: R15 is 44 on the
   machine and 48 by the model.
4. So no one program finds every wrong line. The five programs together reach every join of the
   machine that the lab asks for.

## construction (about 230 words; a short list allowed)

How you build your text in the challenge.

1. The three ways in, each a button above the text (from `4-shared.md`): the outline, the parts,
   nothing. The outline is where it starts.
2. In the outline, six lines are marked with a comment beginning `JOIN:`. Each holds a constant, or
   nothing, where a join belongs. The text elaborates as it is, and runs; every test fails.
3. Each `JOIN:` comment names the join in words, such as where a value comes from. Read it, find
   the wire or the port that carries that value, and write it in place of the constant.
4. In the parts start, every port is listed with nothing in its brackets, such as `.ADDR()`.
   Until a port is joined, the text does not elaborate, and its message names the first port that
   is not joined. You write the small parts between the course's parts too.
5. The wires keep the names the drawing uses: a port usually joins the wire of the same name, but
   not always. Example from the course's text: the memory's port `LOAD` takes the controller's
   `MLOAD`.
6. Press "Run tests" to run all five programs. The first failure to fix is the first in the
   list.

## failureExperiment (about 70 words, above the figure)

1. The figure's text gives the memory's DOOR port `1'b0`, a constant 0, in place of the machine's
   DOOR input. The door never reaches the memory.
2. Run all five programs before reading on. Then read the one sentence that differs, and decide
   which join you would look at.

## failLead (one sentence)

Run the five programs on "DOOR held at 0".

## failAfter (about 120 words, below the figure)

1. Four programs agree: none of them opens the door.
2. The door program: "After `R2 <= R2 + 1` at `014`, "waiting" is 00 on the machine and 10 by the
   model."
3. How to read it: "waiting" bit 1 is the door's event. The model has it after the sixth
   instruction; the machine does not. So the door's event never reached "waiting", which the
   memory keeps. Look at what the memory takes for the door.
4. A sentence of the comparison names a value. Ask which part makes that value, and what that
   part takes in: that is the join to read first.
