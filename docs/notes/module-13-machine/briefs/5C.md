# Brief 5C: lesson `capstone` (Module 13, lesson 5), third part

Read `00-module.md` and `5-shared.md` first; both apply. You may use CPU, machine code,
abstraction, join and trace. It is the course's last lesson: the reflection ends the course.

Keys to write: `explanation`, `generalisation`, `capLead`, `c1Task`, `c1Hints.1` to `c1Hints.5`,
`reflection`, `modelVsReality`.

## explanation (about 160 words)

1. A trace answers a question at one wire and one edge. Each level above it hides that wire: the
   line of the program says what happens to registers; the instruction's word says which fields;
   the datapath says which blocks; only the gate level shows the wire.
2. That hiding is abstraction (do not bold it; lesson 3 introduced it). Each level is enough to
   work out what the level above needs, and no more.
3. The questions of the challenge need the levels below the line: the program's line does not
   say what COUT is, nor which address the memory port reads at a given edge.

## generalisation (about 150 words)

1. Every CPU has the levels this course built: a program, its machine code, a datapath and a
   control unit, and blocks made of gates.
2. Real CPUs have many more parts at each level, but the levels are the same, and a trace goes down
   them the same way.
3. The course's machine is small enough to trace by hand at every level. The CPU in a phone is
   not; its designers rely on the levels to work on one at a time.

## capLead (one sentence, above the challenge)

Write your program, run it on the whole machine, and answer the five questions from its run.

## c1Task (about 200 words; a short list allowed)

1. The task, as `5-shared.md` gives it, with what "colder than -20.0 degrees" means.
2. The program must use at least one set if.
3. The tests of the program: the four pairs of readings and what each must leave, as a short list
   (display and lamps, the lamps as three bits: CLASH, NIGHT, ALARM from left to right).
4. Then the five questions, as a numbered list, as `5-shared.md` gives them, each about the run of
   your program on the whole machine with room A at -184 and room B at -250.
5. Press "Run my program on the whole machine" to trace it. The answers depend on your program;
   no two programs need give the same.

## c1Hints.1 to c1Hints.5 (each one to three sentences; later hints say more, none gives a value)

1. Write the program first and pass its four tests. Two set ifs, one for each room, each compared
   with -200, give two words, each 0 or 1.
2. The count is the sum of the two words. ALARM is 1 when both are 1: the AND of the two, written
   to the lamps.
3. For the first three questions, pause before the ALU edge of your first set if. Y and COUT leave
   the ALU in the datapath; MET leaves the condition block beside it.
4. For the fourth, pause before the MEMORY edge of your first store. ADDR is the address the
   memory port reads; for a store it comes from HR, the address the ALU worked out.
5. For the fifth, pause before the WRITE edge of your first set if. Show the PC's bit 4 from
   "Parts here that never open": D is bit 4 of the address the PC takes next.

## reflection (about 120 words)

1. You started in Module 0 with the machine as a box that runs lines of a program.
2. You built every part: gates, adders, registers, memory, the ALU, the datapath, the control unit,
   the trap hardware, and joined them.
3. You can now follow a line of your own program down to a single gate, at any edge.
4. Ask yourself: which level was hardest to see through, and which level do you now use without
   thinking about the ones below it?

## modelVsReality (about 220 words, with one short code block)

1. What a real machine does that this one does not, named and not taught: it starts the next
   instruction before the last has finished, so several are under way at once; it keeps copies of
   the memory it used last close to the datapath, since the memory is slow; and some instructions
   take many more edges than others.
2. Real designs are also checked with a testbench: a text in the same language that drives the
   machine's inputs, waits, and prints what it sees. Below is a short one for the course's
   machine, to read. Give this block exactly as it is:

```systemverilog
module machine_test;
  logic CLK = 0, RST = 1, DOOR = 0, WARM = 0;
  logic [63:0] SENSORA = -184, SENSORB = -250;
  logic [63:0] PC, DISPLAY;
  logic [2:0] S, LAMPS;
  logic HALT;
  logic [7:0] CAUSE;

  machine m (.*);

  always #5 CLK = ~CLK;

  initial begin
    #12 RST = 0;
    wait (HALT);
    $display("display %0d, lamps %b", $signed(DISPLAY), LAMPS);
    $finish;
  end
endmodule
```

3. In words: `.*` joins each of the machine's ports to the wire of the same name; `always #5`
   turns the clock over every 5 units of simulated time; `initial` runs its lines once, from the
   start; `#12` waits 12 units, so the reset holds over the first rising edge; `wait (HALT)` waits
   until the machine halts; `$display` prints the display and the lamps.
4. The course's engine does not run this text: it describes a test, not hardware. Tools that
   simulate SystemVerilog run it. They would also need the text of each of the course's parts,
   which the course's engine builds itself, and the program in the ROM.
