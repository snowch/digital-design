## The run the timeline shows (the handler's load faults)

```
handler: word[0x400] <= R8      // 01C
        ...
room:   R8 <= R2 + R2           // 03C
        R8 <= R8 + R8
        R8 <= R8 + R8
        R1 <= word[R8 + 0x7D8]  // 048
        goto back
fault:  R8 <= C2                // 050: skip what faulted, as lesson 1's handler did
        R8 <= R8 + 4
        C2 <= R8
back:   R8 <= word[0x400]       // 05C
        R9 <= word[0x408]
        resume                  // 064
program: R2 <= 5                // 068
        R1 <= 2
        call system             // 070
```

- Edge 10: the `call system` at `070` traps with cause `41`: C2 ← `074`, C1 ← `00`, C0 ← `01`,
  C3 ← `41`, PC ← `01C`.
- Edges 18 to 20: R8 becomes 10, 20, then 40.
- Edge 21: the load at `048` traps with cause `31`: C2 ← `048`, C1 ← `01`, C0 ← `01`, C3 ← `31`,
  PC ← `01C`. The handler starts again from its first line.
- Edges 22 and 23: the handler saves R8 and R9 again, at `400` and `408`, over the program's
  words saved there at edges 11 and 12.
- Edges 27 to 29: the fault part sets C2 to `04C`. Edge 32: `resume` goes to `04C` in system
  mode (C0 ← `01`), the handler's `goto back`.
- From there the handler goes round four lines for ever: `goto back`, the two loads, `resume` to
  `04C`. The program never runs again. The debugger would cut the run off after 5000 instructions.

## timelineAfter (about 80 words, shown once the learner has stepped to the last edge)

## c1Task (numbered list)

1. The user program's `call system` at `108` asks for job 5. While the loop runs, the door's
   interrupt comes before `R2 <= R2 - 1` at `088`. Give, in hexadecimal:
   - what C1 holds just after the door's interrupt;
   - what C3 holds just after it;
   - the word at `418` just after it;
   - what C0 holds after the door part's `resume`.
2. C1 and C0 as two digits, C3 as two, the word as three. There are 4 tests, one for each answer.

The answers (for your hints): `11`, `82`, `10C`, `11`.

## c1Hints (five, in this order)

1. The idea: the interrupt's edge copies C0 into C1, and C0 in the loop is what job 5 wrote.
2. A common mistake: giving C1 as `10`, the user program's status. C1 takes C0 as it is when the
   interrupt comes, and the handler is running.
3. A smaller example: in the timeline, the load's trap in the handler gave C1 `01`, the handler's
   C0 at that moment.
4. Part of the answer: the word at `418` holds what C2 held when job 5 began, the return point of
   the `call system` at `108`.
5. The whole answer: `11`, `82`, `10C` and `11`.

## The run the failure experiment shows (job 5 turns interrupts on but keeps nothing)

Job 5 writes 3 to C0 and waits, but does not keep C1 and C2. The door opens once 60 instructions
have run. The door's interrupt comes in the loop, after 61 instructions, at `078`; the timer's
after 90, at `078` again; ALARM lights. Each wrote C2 ← `078` and C1 ← `11`. When the loop ends,
job 5's `resume` goes to `078`, the loop, in system mode, with R2 at 0: counting down from 0, the
loop would take far more than 5000 instructions to reach 0 again. The debugger cuts the run off after 5000 instructions. The display
shows 5: the program never showed 6 or ended.

## failureExperiment (about 50 words)

2. The door opens once 60 instructions have run, during the wait.
