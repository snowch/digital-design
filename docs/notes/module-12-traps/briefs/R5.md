## unseenAfter (about 90 words; shown once the run has ended)

1. The program shows 30 and ends: the handler's `stop` for job 4 ends the run at `054`, after 92
   instructions.
2. The panel shows "Door opened: yes".
3. "Waiting" is the word at `7F0`, with one bit for each event: bit 0 for the timer, bit 1 for the
   door. The door opened after 15 instructions. Its bit was set at the edge that ended the 16th,
   the first instruction to run with the door open. Nothing cleared it: bit 1 is still set.
4. No line of the program or the handler read the door. The program cannot touch a device in user
   mode, and the handler runs only when the program traps.

## motivation (about 170 words)

1. The machine can go to the handler without the program asking. At the edge that would run the
   next instruction, if a bit of "waiting" is set and C0's bit 1 is 1, the machine traps instead.
2. A trap that an event outside the program makes, between two of its instructions, is an
   **interrupt**. C0's bit 1 says whether interrupts are on.
3. The cause says which event: `81` means the timer reached 0, and `82` means the door opened. If
   both bits are set, `81` goes first: the lower number wins.
4. The interrupt's edge makes the five transfers every trap makes: C2, C1, C0, C3 and the PC. C0
   takes `01`, so interrupts are off in the handler.
5. Do not say what C2 takes at an interrupt: the prediction asks it.
6. The handler clears an event's bit by writing a 1 to it. Storing 1 to `waiting` clears the
   timer's bit, and storing 2 clears the door's. For the door, the handler writes `R8 <= 2`, then
   `word[waiting] <= R8`.
7. The start turns interrupts on for the program by writing 2 to C1 instead of 0: C1 is then `10`,
   bit 1 on, bit 0 off, user mode. `resume` then does what lesson 1 said: the PC takes C2, and C0
   takes C1.
8. Interrupts are taken in user mode and in system mode alike, whenever C0's bit 1 is 1.

## noClearAfter (about 90 words; shown once the run has ended)

1. The debugger cut the run off after 5000 instructions. After the door's interrupt, all of them
   were the handler's, and 384 traps went to the handler.
2. R2 stays at 4, and the display shows 0.
3. The door part never clears the door's bit, so the bit stays set. `resume` takes the PC back to
   `0B0`, and the edge after each `resume` traps again, with cause `82`, before `0B0` runs.
4. Each visit sets the timer to 20 again, so the timer never reaches 0, and ALARM never lights.
5. A handler must clear the event it answers.

## c2Task (a numbered list)

1. The starting text holds the whole handler except the timer's part, which only goes to `back`.
   Its start lights NIGHT before the program runs.
2. Write the timer's part at `tick:`. It clears the timer's bit of "waiting", bit 0. Then, if the
   door is still open, it lights ALARM and leaves the other lamps as they are, so NIGHT stays lit.
   If the door has closed, it leaves the lamps alone. Either way it ends by going to `back`.
3. The door is bit 0 of the word at `7D0`, which the assembler names `signals`; bit 1 is WARM. The
   lamps can be read as well as written, with `word[lamps]`.
4. An interrupt may change no register: the program did not ask for it. The timer's part may write
   R8 and R9, which the handler saves at its start and puts back at `back`.
5. There are 5 tests. Each adds a program after yours, named `program`. It puts its own words in
   R0 and R5 to R15, counts to 30 in R2 over 30 rounds, copies R8 and R9 into R12 and R13, shows R2
   with job 1, and ends with job 4. Each test opens the door at its own time: left open; closed in
   time; never opened; opened late and left open; left open on a warm night, with WARM 1.
6. Each test checks the lamps; that the display shows 30; R0 and R3 to R15 at the end, with R12
   and R13 holding R8 and R9 as the program found them; the causes in order; and that the run
   ends at the handler's `stop` for job 4.

## c2Hints (five, a ladder; each begins with its rung's words)

1. "The idea:" clear bit 0 of "waiting" by storing 1 to it. Read `signals`, keep bit 0 with `&`,
   and compare it with 1. To light ALARM beside the other lamps, read the lamps, set bit 0 with
   `|`, and store them back.
2. "A common mistake:" storing 1 to the lamps. That lights ALARM but puts NIGHT out. Comparing the
   whole of `signals` with 1 is another: on a warm night WARM's bit is set too.
3. "A smaller example:" to put ALARM out and leave the other lamps as they are, a part would read
   `word[lamps]`, `&` it with 6, and store it back.
4. "Part of the answer:" the part starts as the figures' timer part does: `R8 <= 1`,
   `word[waiting] <= R8`, `R8 <= word[signals]`, `R9 <= 1`, `R8 <= R8 & R9`, then
   `if R8 != R9 goto back`.
5. "The whole answer:" then this, in a fenced code block, exactly as given:

```
tick:   R8 <= 1
        word[waiting] <= R8     // the timer's event is seen
        R8 <= word[signals]
        R9 <= 1
        R8 <= R8 & R9           // DOOR
        if R8 != R9 goto back   // closed in time
        R8 <= word[lamps]
        R8 <= R8 | R9           // ALARM, beside the lamps already lit
        word[lamps] <= R8
        goto back
```
