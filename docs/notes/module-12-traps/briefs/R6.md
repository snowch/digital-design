# Brief R6: lesson `nesting` (Module 12, lesson 6), after the reading review

Read `00-module.md` (the shared fact sheet) first, including its last section, "Decisions after
the reading review"; it applies here. You may use **trap**, **handler**, **user mode**, **system
mode**, **system call** and **interrupt** (earlier lessons; never bold). "The start" (not a term)
is the lines from reset that set C4 and start the program. "Save" and "put back" are the words for
copying C1, C2, R8 or R9 to the RAM and back; never "keep" for that.

## motivation (about 130 words)

1. A handler can let interrupts in, by writing 3, `11`, to C0. Then an interrupt can come while the
   handler runs.
2. A fault in the handler's own lines is a trap too, and it can come whether interrupts are on or
   off.
3. A trap inside the handler is like any other. Its edge writes C2, C1, C0 and C3, and the PC takes
   C4, the handler's address. The handler starts again from its first line.
4. C2 held the program's return point, and C1 the program's status. The second trap writes over
   them both. Unless the handler saved them first, the way back to the program is lost.
5. Do not say how the handler saves them: the explanation does.

## construction (about 60 words)

1. The listing is the first figure's handler, with job 5 changed.
2. Job 5 saves C1 at `410` and C2 at `418`, writes 3 (`11`) to C0, waits, writes 1 (`01`) to C0,
   and puts C1 and C2 back before `resume`.
3. The door opens during the wait.

## explanation (about 150 words; one list)

1. A handler that lets interrupts in takes four steps (a list):
   - saves C1 and C2 in two RAM words of its own;
   - writes 3 to C0;
   - writes 1 to C0 when it is done, so nothing can come in while it puts C1 and C2 back;
   - puts C1 and C2 back, then runs `resume`.
2. The handler saves R8 and R9 at its start, at `400` and `408`. A trap inside the handler saves
   them there again. So job 5 puts the program's R8 and R9 back before it lets interrupts in.
   After that it uses only R1 and R2, the call's own registers, which lesson 4 said a system call
   may change.
3. A fault in the handler has no fix of this kind. The handler must check what a program gives it,
   such as a room number, before it uses it.
4. An event that comes in while interrupts are off is not lost: its bit in "waiting" stays set, as
   lesson 5 showed, until the handler clears it.
5. The figure runs job 5 as it should be. It shows the words at `410` and `418`, and lets you
   choose when the door opens.

## c2Hints (five, a ladder; each begins with its rung's words)

1. "The idea:" job 6 takes the explanation's four steps: save C1 and C2, write 3 to C0, count,
   write 1 to C0, put C1 and C2 back, then `resume`.
2. "A common mistake:" writing 3 to C0 and nothing else. The door's interrupt writes over C1 and
   C2, and the program goes on in system mode, or never comes back.
3. "A smaller example:" lesson 2's handler saved R5 with `word[0x408] <= R5` before it changed R5.
   A control register is saved through an R register: `R1 <= C2`, then a store of R1.
4. "Part of the answer:" put the program's R8 and R9 back from `400` and `408` first, since a trap
   in the count saves them there again, and count with R1 and R2 only.
5. "The whole answer:" job 6, from `count:` to its `resume`, then this, in a fenced code block,
   exactly as given:

```
count:  R8 <= word[0x400]       // the program's R8 and R9 back now:
        R9 <= word[0x408]       // a trap in the count saves them again
        R1 <= C1
        word[0x410] <= R1       // save C1
        R1 <= C2
        word[0x418] <= R1       // save C2
        R1 <= 3
        C0 <= R1                // system mode, interrupts on
        R1 <= 0
next:   word[display] <= R2     // show the count
        R2 <= R2 - 1
        if R2 != R1 goto next
        R1 <= 1
        C0 <= R1                // interrupts off again
        R1 <= word[0x410]
        C1 <= R1                // C1 and C2 put back
        R1 <= word[0x418]
        C2 <= R1
        resume
```
