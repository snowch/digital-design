# Brief 8C: lesson `system-call-mechanism` (Module 12, lesson 8), third part

Read `00-module.md` first, then "Facts every part of this lesson may use" in `8A.md`; both apply.
You may use **trap**, **handler**, **user mode**, **system mode**, **system call** and
**interrupt** (never bold them).

Keys to write: `explanation`, `generalisation`, `challenge`, `runLead`, `c1Task`, `c1Hints.1` to
`c1Hints.5`, `reflection`, `modelVsReality`.

## explanation (about 150 words)

1. The handler is the only program that runs in system mode. Every user program reaches the
   display, the sensors and the lamps only through its jobs, and every mistake a program makes
   comes back to it as a trap.
2. A program ends in one of two ways: it asks, with job 4, or it faults. Both lead to the same
   lines: record, next number, start. The record is the cause, so the shop can read why a
   program ended.
3. Lessons 1 to 6 each gave one part: the trap and `resume` (lesson 1), saving registers (2),
   user mode (3), system calls (4), the handler's own state kept in memory, and trusting nothing a
   program gives (6). Interrupts (5) are off in these runs.

## generalisation (about 110 words)

1. A handler that runs programs one after another, gives them jobs and ends them when they fault
   is the core of what a real machine calls its operating system. Do not use the words
   "operating system" or "kernel": say "the program a real machine runs first, which runs all the
   others".
2. Everything it needs is on this machine: C0 to C4, `resume`, user mode and `call system`.
3. What it does not do here: share the machine between programs that run at the same time. With
   the timer's interrupt, a handler could stop one program and resume another; that is beyond
   this module.

## challenge (about 60 words)

2. Choose one with the challenge's own control.

## runLead (one sentence)

Write the handler, step through it on the tests' programs, then run the tests.

## c1Task (numbered list)

1. Write a handler that runs each program the table `programs` names, in order, in user mode with
   interrupts off. The tests add the table and the programs after it.
2. Offer jobs 1 to 4 by `call system`: 1 shows R2; 2 puts room R2's reading in R1 (0 for room A,
   1 for room B, 0 for any other R2); 3 sets the lamps from R2; 4 ends the program.
3. A program that faults ends there. For program k, leave 0 at `0x400 + 8k` if it ended with
   job 4, or its cause if it faulted.
4. Keep every register but R1 for the program across a job. After the last program, stop.
5. There are 6 tests. Room A reads -184 and room B -250. Each checks the words shown, the lamps,
   each program's record, and that the run ends at a `stop`.

## c1Hints (five, in this order)

1. The idea: keep the number of the program running in a RAM word; the start reads it, finds the
   program's address in the table, writes 0 to C1 and the address to C2, and runs `resume`.
2. A common mistake: running `stop` for job 4. That stops the machine; job 4 ends the program and
   the handler starts the next.
3. A smaller example: lesson 4's handler chose the job with `R8 <= 1` and
   `if R1 == R8 goto show`, after checking C3 for `41`.
4. Part of the answer: the program's address is `word[programs + 8 + 8k]`. Multiply k by 8 by
   adding it to itself three times, add `programs`, then load with `word[R1 + 8]`.
5. The whole answer: the guided start's lines, with these parts in place of its stubs:

```
room:   R1 <= word[sensorA]     // job 2: room A when R2 is 0
        R8 <= 0
        if R2 == R8 goto back
        R1 <= word[sensorB]     // room B when R2 is 1
        R8 <= 1
        if R2 == R8 goto back
        R1 <= 0                 // no such room
        goto back
light:  word[lamps] <= R2      // job 3: the lamps from R2's bits 2 to 0
        goto back
...
finish: R9 <= 0                 // job 4: the program ended; its record is 0
ended:  R8 <= word[0x480]       // record R9 for program R8, at 0x400 + 8 × R8
        R1 <= R8 + R8
        R1 <= R1 + R1
        R1 <= R1 + R1
        word[R1 + 0x400] <= R9
        R8 <= R8 + 1
        word[0x480] <= R8       // the next program
        goto start
```

(In c1Hints.5, say that `back:` stays as the guided start has it, between `light:` and
`finish:`; the `...` in the block stands for it.)

## reflection (about 70 words; do not write the words "End on the question")

1. The machine now runs the shop's programs: logic gates, registers, a datapath, a controller,
   an instruction set, programs, and a handler over them.
2. Every part was built, but in separate lessons, on separate drawings.
3. The question: can you follow one of the shop's programs through the handler and down to the
   gates of the one machine that runs it?

## modelVsReality (about 70 words)

1. A real machine's first program does what this handler does, with far more: it loads programs
   from storage, gives each its own memory, and switches between them on the timer's interrupt.
2. Real machines protect each program's memory from the others; this one protects only the
   devices and the control registers.
3. Its jobs are numbered as this handler's are, and a program asks for them with one
   instruction.
