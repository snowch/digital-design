## motivation (about 220 words; one list)

1. The handler has five parts (a list):
   - The start sets C4, then runs the program whose number the word at `480` holds, counting from
     0. It finds the program's address in the table `programs`, which the tests add after the
     handler: its first word is how many programs, then each program's address. It runs the
     program in user mode with interrupts off, by writing C1 and C2, then running `resume`.
   - The choice reads C3 to tell a system call from a fault, and R1 to find the job.
   - The jobs: job 1 shows R2; job 2 puts a room's reading in R1; job 3 sets the lamps from R2's
     bits 2 to 0; job 4 ends the program.
   - The end of a program writes its record, at `400` plus 8 times its number. Then it moves to
     the next number and goes back to the start.
   - The stop comes after the last program, and it stops the machine.
2. The number lives in the RAM, in the word at `480`, because a register is a program's to change.
   The RAM is not protected either: a user program could store over that word, as lesson 3's
   program stored over the handler's count. The word at `480` is safe only from the program's
   registers.
3. Job 2 checks R2, because lesson 6 taught that a handler must not trust what a program gives it.
   R2 is 0 for room A and 1 for room B. Any other value gives 0, so no program can make the
   handler read a word that is not a sensor.
4. A job may change R1 and R2 only, the call's own registers, as lesson 4 said. The handler keeps
   every other register for the program.

## p1Explain (about 70 words; shown after the learner commits)

1. The word at `400` holds 51. The load faults with cause `33`, and the handler stores C3, the cause
   itself, as a word.
2. A word is written as a decimal number, and `33` in hexadecimal is 3 × 16 + 3 = 51.
3. 33 is the cause's digits read as a decimal number, which no store writes. 0 would mean the
   program ended with job 4, which it never reached. 52 would be cause `34`, a store the machine
   refuses.

## explanation (about 150 words)

1. The handler is the only program that runs in system mode. Every user program reaches the
   display, the sensors and the lamps only through its jobs. Everything user mode refuses comes
   back to the handler as a trap; a mistake user mode allows, such as a store into the RAM or a
   loop that never ends, does not.
2. A program ends in one of two ways. It asks for job 4, or it faults. Both lead to the same lines:
   record, next number, start. A fault's record is its cause, kept as a word, so the shop can read
   why the program ended: cause `32` reads 50. A program that ends with job 4 records 0.
3. Lessons 1 to 6 each gave one part. Lesson 1 gave the trap and `resume`. Lesson 2 gave saving
   registers. Lesson 3 gave user mode. Lesson 4 gave system calls. Lesson 6 gave the handler's own
   state, saved in memory, and the rule to trust nothing a program gives it. Interrupts (lesson 5)
   are off in these runs.

## c1Task (a numbered list)

1. Write a handler that runs each program the table `programs` names, in order, in user mode with
   interrupts off. The tests add the table and the programs after it.
2. Offer jobs 1 to 4 by `call system`. Job 1 shows R2. Job 2 puts a room's reading in R1: R2 is 0

3. A program that faults ends there. For program k, counting from 0, write its record to the word

5. There are 7 tests. Room A reads -184 and room B -250. Each checks the words shown, the lamps,
   each program's record, C1 at the end (the last program's mode at its last trap, `00`), and
   that the run ends at the handler's `stop`.

## c1Hints (five, a ladder; each begins with its rung's words)

1. "The idea:" keep the number of the program running in the RAM word at `480`. The start reads
   that word, finds the program's address in the table, writes 0 to C1 and the address to C2, and
   runs `resume`.
2. "A common mistake:" running `stop` for job 4. That stops the machine. Job 4 ends the program,
   and the handler starts the next one.
3. "A smaller example:" a table named `t` holds its first word at `t` and its second at `t` plus 8,
   so `R1 <= t` then `R1 <= word[R1 + 8]` loads its second word.
4. "Part of the answer:" the program's address is the word at `programs + 8 + 8k`. Multiply k by 8
   by adding it to itself three times: each addition doubles it. Add `programs`, then load with
   `word[R1 + 8]`.
5. "The whole answer:" the outline's lines, with these two parts in place of its stubs, each in a
   fenced code block exactly as given. The start, in place of `start:  stop`:

```
start:  R1 <= word[0x480]       // run program number R1, if there is one
        R2 <= word[programs]
        if R1 == R2 goto done
        R1 <= R1 + R1
        R1 <= R1 + R1
        R1 <= R1 + R1           // 8 × R1
        R2 <= programs
        R1 <= R1 + R2
        R1 <= word[R1 + 8]      // its address, from the table
        C2 <= R1
        R1 <= 0
        C1 <= R1                // user mode, interrupts off
        resume
done:   stop
```

   And the end of a program, in place of `finish: stop` and `ended:  stop`:

```
finish: R9 <= 0                 // job 4: the program ended; its record is 0
ended:  R8 <= word[0x480]       // record R9 for program R8, at 0x400 + 8 × R8
        R1 <= R8 + R8
        R1 <= R1 + R1
        R1 <= R1 + R1
        word[R1 + 0x400] <= R9
        R8 <= R8 + 1
        word[0x480] <= R8       // the next program
        goto start
```
