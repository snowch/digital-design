# Brief R3: lesson `user-mode` (Module 12, lesson 3), after the reading review

Read `00-module.md` (the shared fact sheet) first, including its last section, "Decisions after
the reading review"; it applies here. You may use **trap** and **handler** (lesson 1; not bold).
This lesson introduces **user mode** and **system mode**: bold each once, in the motivation, as
now; nowhere else bold.

One new name for this page: **the start** (not bold, not a term) means the lines from reset, at
`000`, that set C4 and start the program. They run once, from reset. "The handler" is only the
code at the address C4 holds, named `handler:`. Never call the start "the handler" or "the
handler's start".

Each key below replaces the page's text for that key. Write each from its facts alone.

Keys to write: `question`, `systemLead`, `motivation`, `prediction`, `p1Explain`, `investigation`,
`timelineLead`, `explanation`, `mapLead`, `userLead`, `c2Task`, `c2Hints.1` to `c2Hints.5`, and
the labels `captions.predict`, `captions.user`, `userLabels.1` to `userLabels.4`, `memoryTitle`.

## motivation (about 160 words; one list)

1. C0's bit 0 sets the mode.
2. When bit 0 is 1, the machine refuses only what Module 8's machine refused. That is **system
   mode**. Every program so far ran in it.
3. When bit 0 is 0, the machine refuses more. That is **user mode**. In user mode these faults
   come with these causes (a list):
   - `resume`, the two control-register jobs, and `stop`: cause `22`;
   - every load or store at a device's address, `7C0` to `7F7`: cause `32`.
4. Every other instruction runs as before, in the ROM and the RAM.
5. A trap's edge sets C0 to `01`, so the handler always runs in system mode. C1 takes C0 at that
   edge, so it keeps the mode the program was in.
6. The start runs a program in user mode with lesson 1's `resume`. It writes 0 to C1 and the
   program's address to C2, the return point, then runs `resume`. At `resume`'s edge C0 takes C1,
   and the PC takes C2.

## prediction (about 50 words)

2. The program stores to room B's sensor, which the machine refuses.
3. The handler keeps the cause at `400`, then stops.
4. Last sentence: Choose an answer and press "Check my prediction".

## p1Explain (about 70 words; shown after the learner commits)

1. C1 holds `01` just after the store traps: C0 as it was when the store faulted.
2. `goto` changes only the PC, so C0 was still `01` and the program ran in system mode. The 0 the
   start wrote to C1 was never used: the trap's edge wrote over it.
3. The cause is `34`, a store to a read-only device, not `32`: in system mode the machine refuses
   the store for the sensor's sake, not the mode's.
4. A start reaches user mode only through `resume`, which copies C1 into C0.

## explanation (about 110 words)

1. In user mode the machine refuses whatever reaches the shop's devices or the control registers,
   and `resume` and `stop`. It does not refuse the RAM: the last figure's program wrote the
   handler's count.
2. Without `resume` or a control-register job, a user program cannot set C0 back to system mode,
   or change C4. The line that would set C0, `C0 <= R1`, traps with cause `22`.
3. Without `stop`, a user program cannot stop the machine. Its `stop` traps, and the handler
   decides what happens next.
4. `resume` gives the program back the mode C1 holds.
5. The figure shows the memory map as user mode meets it.

## c2Task (a numbered list)

1. The starting text's start sets C4, sets the count in the word at `400` to 0, and goes to
   `program` with `goto`. Its handler only stops.
2. Change the start so that `program` runs in user mode.
3. Write the handler. On cause `32`, a device's address refused, it adds 1 to the count at `400`
   and skips the instruction. On any other cause, it keeps the cause in the word at `408`, then
   runs `stop`.
4. The count is `word[0x400]` and the kept cause `word[0x408]`, as you type them.
5. There are 4 tests. Each adds a program after yours, named `program`, which reaches a device,
   or does something else user mode or the machine refuses.
6. Each test checks C1 at the end of the run, which holds the program's mode at its last trap;
   the count at `400`; the cause kept at `408`; the causes in order; and that the run ends at the
   handler's `stop`.

## c2Hints (five hints, a ladder; each begins with its rung's words)

1. "The idea:" a start reaches user mode only with `resume`, after writing C1 and C2. The handler
   reads C3 first and compares it with `0x32`.
2. "A common mistake:" `goto program`. The program then runs in system mode, as the prediction
   showed, and a device's address does not trap.
3. "A smaller example:" a start that runs a line named `later` in system mode with `resume`
   writes 1 to C1 and `later`'s address to C2, then runs `resume`.
4. "Part of the answer:" lesson 1's challenge counted and skipped one cause and stopped on the
   others; this handler does the same for cause `32`, and keeps the other cause at `408` before
   its `stop`.
5. "The whole answer:" then this program, in a fenced code block, exactly as given:

```
        R1 <= handler
        C4 <= R1
        R1 <= 0
        word[0x400] <= R1       // the count of device accesses refused
        C1 <= R1                // user mode, for the program resume starts
        R1 <= program
        C2 <= R1
        resume
handler: R5 <= C3
        R6 <= 0x32
        if R5 != R6 goto other
        R5 <= word[0x400]
        R5 <= R5 + 1
        word[0x400] <= R5
        R5 <= C2
        R5 <= R5 + 4
        C2 <= R5
        resume
other:  word[0x408] <= R5       // keep the cause
        stop
```
