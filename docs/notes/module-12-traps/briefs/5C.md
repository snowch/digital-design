lesson may use" in `5A.md`, and the handler in `5B.md`; all apply here. You may use **trap**,
**handler**, **user mode**, **system mode**, **system call** and **interrupt** (never bold them).

Keys to write: `explanation`, `debuggerLead`, `debuggerAfter`, `generalisation`, `timerLead`,

## explanation (about 150 words; a short table allowed)

1. A table of the three ways into the handler, columns: what makes it; its cause; its return
   point.
   - a fault: the instruction the machine refuses; `11` to `34`; the instruction that faulted;
   - a system call: `call system`; `41`; the next instruction;
   - an interrupt: an event, with interrupts on; `81` or `82`; the instruction not yet run.
2. An interrupt comes between two instructions, never inside one. The instruction before it has
   finished; the one after it has not started. So the program's registers and memory are as any
   edge leaves them, and `resume` carries on as if nothing had happened.
3. The handler must leave the program's registers as it found them, as lesson 2 showed: this one
   saves R8 and R9.
4. The handler clears the bit of the event it answers. An event that waits while interrupts are
   off is not lost: its bit stays set until the handler clears it.
5. The figure runs the program in the debugger with a breakpoint on each event's part, and lets
   you choose when the door opens.

## debuggerAfter (about 50 words, shown once the run has ended)

Facts, for a door that opens (after 5, 15 or 50 instructions): the display shows 30, ALARM is on,
132 instructions ran and 4 traps went to the handler. With "never", no interrupt comes: 101
instructions and 2 traps, the two `call system`, and ALARM stays off. Say both briefly.

## generalisation (about 110 words)

1. An interrupt lets the machine answer an event at once without the program checking for it.
   A program that checked the door itself would have to read it again and again, and a user
   program may not read it at all.
2. The handler start chooses whether the program may be interrupted, by C1's bit 1. Every trap's
   edge turns interrupts off, so the handler is not interrupted unless it turns them on.
3. Each event has its bit and its cause. The handler tells them apart by C3, as it tells a fault
   from a system call.
4. The timer is how a handler waits without stopping the program: it sets a count and answers when
   the count reaches 0.

## c2Task (numbered list)

1. The starting text holds the whole handler but the timer's part, which only goes to `back`.
2. Write the timer's part, at `tick:`. It clears the timer's bit of "waiting". Then, if the door is
   still open (bit 0 of `signals`), it lights ALARM; if the door has closed, it leaves the lamps
   alone. Either way it ends by going to `back`.
3. There are 4 tests. Each adds the counting program after yours, named `program`, and opens the
   door at its own time: left open; closed in time; never opened; opened late and left open. Each
   checks the lamps, that the display shows 30, and that the run ends at a `stop`.

## c2Hints (five, in this order)

1. The idea: read `signals` into R8, keep bit 0 with `&`, and compare it with 1.
2. A common mistake: lighting ALARM at every timer's interrupt. The door may have closed in time.
3. A smaller example: the door's part clears its bit with `R8 <= 2` and `word[waiting] <= R8`; the
   timer's bit is bit 0, so the timer's part stores 1.
4. Part of the answer: `R8 <= word[signals]`, `R9 <= 1`, `R8 <= R8 & R9`, then
   `if R8 != R9 goto back`.
5. The whole answer:

```
tick:   R8 <= 1
        word[waiting] <= R8     // the timer's event is seen
        R8 <= word[signals]
        R9 <= 1
        R8 <= R8 & R9           // DOOR
        if R8 != R9 goto back   // closed in time
        word[lamps] <= R9       // still open: ALARM
        goto back
```

## reflection (about 70 words; end on the question)

1. Every trap's edge turns interrupts off, so a door that opens while the handler runs waits until
   `resume`.
2. A handler that runs for a long time, with a long job, keeps the door waiting all that time.
3. And a handler can fault, like any program.
4. End on the question: what happens if a trap comes while the handler runs?

## modelVsReality (about 70 words)

1. Real machines take interrupts between instructions, as this one does, from many devices: disks,
   networks, keyboards, timers.
2. Many give each device a number and a table of handler addresses, and let some devices
   interrupt others.
3. A real timer counts time, not instructions. This machine's counts instructions, so every run
   with the same door is the same.
