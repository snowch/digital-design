# Brief 1C: lesson `traps` (Module 12, lesson 1), third part

Read `00-module.md` (the shared fact sheet) first; it applies here. You may use **trap** and
**handler** (introduced earlier in this lesson; do not bold them again).

Keys to write: `explanation`, `debuggerLead`, `debuggerAfter`, `generalisation`, `skip34Lead`,
`c2Task`, `c2Hints.1` to `c2Hints.5`, `reflection`, `modelVsReality`.

## explanation (about 150 words; a short list allowed)

1. The return point is where `resume` goes. After a fault, it is the instruction that faulted.
2. The handler then has two choices:
   - mend what went wrong and run the instruction again, with C2 as it is;
   - skip the instruction, by adding 4 to C2 before `resume`.
3. The night program's handler skips: `R5 <= C2`, `R5 <= R5 + 4`, `C2 <= R5`.
4. C2 is a register like any other to the handler: it reads it with `R5 <= C2` and writes it with
   `C2 <= R5`. The same two jobs read and write C0, C1, C3 and C4.
5. With C4 at 0, as at reset, a trap has nowhere to go: the machine halts with the cause, as it
   did in every module before this one. Every program from Modules 8 to 11 ran with C4 at 0.
6. A trap at the address C4 holds also halts the machine: a handler that faults on its own first
   instruction would trap there for ever.

## debuggerLead (about 50 words; numbered steps)

1. The debugger runs the night program with the control registers shown and a breakpoint on the
   handler's first line.
2. Press "Run to a breakpoint". The run pauses at the handler: read C2, C3 and C4.
3. Step through the handler and watch C2 change.

## debuggerAfter (about 40 words, shown once the run has ended)

1. The program stops at `020` with NIGHT on and -184 on the display.
2. The status line says 14 instructions ran and 1 trap went to the handler.
3. The word at `400` holds 52: cause `34` read as a decimal number.

## generalisation (about 120 words)

1. Every cause goes to the same handler, at the address C4 holds. The handler reads C3 to tell the
   causes apart.
2. One handler address serves every cause on this machine. Some machines keep a table of
   addresses instead, one for each cause.
3. A fault returns to the instruction that faulted. Lesson 4 meets a trap whose return point is
   the instruction after it.
4. The handler is an ordinary program in the ROM, written in the same assembly. The machine adds
   only the five transfers at the trap's edge and the two at `resume`'s edge.

## skip34Lead (one sentence)

Write the handler, step through it on the tests' programs, then run the tests.

## c2Task (numbered list)

1. Write a handler that skips every store the machine refuses, cause `34`, and counts them in the
   word at `0x400`.
2. On any other cause, the handler runs `stop`, so the machine stops there.
3. The starting text sets C4, sets the count to 0 and goes to `program`. Its handler only resumes.
4. There are 4 tests. Each adds its own program after yours, named `program`, and runs the whole
   from reset. Each checks the count, the display, how many traps went to the handler, and that
   the run ends at a `stop`.

## c2Hints (five, in this order)

1. The idea: read the cause with `R5 <= C3` and compare it with `0x34` before doing anything else.
2. A common mistake: counting every trap. Only a refused store, cause `34`, is counted and
   skipped.
3. A smaller example: the night program's handler skips with `R5 <= C2`, `R5 <= R5 + 4` and
   `C2 <= R5` before `resume`.
4. Part of the answer: `R6 <= 0x34` then `if R5 != R6 goto other`, with `other: stop` at the end.
5. The whole answer:

```
        R1 <= handler
        C4 <= R1
        R1 <= 0
        word[0x400] <= R1       // the count of refused stores
        goto program
handler: R5 <= C3
        R6 <= 0x34
        if R5 != R6 goto other
        R5 <= word[0x400]
        R5 <= R5 + 1
        word[0x400] <= R5
        R5 <= C2
        R5 <= R5 + 4
        C2 <= R5
        resume
other:  stop
```

## reflection (about 70 words; end on the question)

1. The night program did not use R5. The handler wrote R5 three times.
2. A handler runs in the middle of another program, which may keep its own words in R5.
3. End on the question: what must a handler leave as it found it, and where can it keep words while
   it works?

## modelVsReality (about 70 words)

1. Real machines go to a handler as this one does: a register for the return point, one for the
   cause, and the handler's address.
2. Many keep a table of handler addresses, one for each cause, in memory.
3. This machine takes one edge for a trap, as it does for each instruction.
