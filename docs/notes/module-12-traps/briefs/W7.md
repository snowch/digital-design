## motivation (about 330 words; one list of four)

1. Each part sits in the datapath or the control unit. To see a part, press the block it sits in:
   a block opens to show the parts inside. Each block is drawn with its title, written in code
   form, such as `datapath-traps`. The list names the blocks to press for each part, by those
   titles.
2. Four parts change for a trap (a list):
   - The control registers, C0 to C4, each with a selector that picks its next word: press
     `datapath-traps`, then `control-registers`. The selector `returnPoint` picks C2's word at a
     trap: the PC plus 4 when the cause's bit 6 is 1, and only cause `41`, a system call, has that
     bit set. Otherwise it picks the PC itself.
   - The next PC, which takes C4 at a trap's edge, C2 at `resume`'s edge, and otherwise what
     Module 9 gave it: press `datapath-traps`, then `next-trap`.
   - The trap logic, in the control unit where the stop logic was: press `control-unit-traps`,
     then `trap-logic`. It reads the three causes (CAUSEF, CAUSED and CAUSEM), STOP, CHECKING,
     FETCHING, the bits of "waiting", IE and NOHANDLER. IE is C0's bit 1; when it is 1,
     interrupts are on. NOHANDLER is 1 when C4 is 0, or when C4 holds the PC. It sets GO, TRAP,
     CAUSE and HALT.
   - The controller, in the control unit: press `control-unit-traps`, then `controller-traps`.
     `resume` and a control-register copy (such as `R5 <= C2`) now go from READ to WRITE, as a
     function call does. It has one more new rule, for an edge that traps. (Do not say what the
     rule is, and do not mention the prediction.)
3. The mode is C0's bit 0, and it goes to two places. The decoder gives cause `22` in user mode
   for `resume`, the control-register copies and `stop`. The memory port's checks give cause `32`
   in user mode for a device's address.
4. Every part takes its word at the same edge: the last edge of the instruction that traps. The
   trap takes no edge of its own.
5. The drawings are large. On a phone, scroll inside a drawing, or use its overview to move about.

## p1Explain (about 100 words)

1. The controller goes to FETCH. At an edge that traps, its state register takes FETCH, whatever
   its table says, as it does at a reset.
2. The table's move from READ is to ALU. The trap overrides that move: the `call system` ends at
   its READ edge, which is its second edge.
3. Before that edge, while TRAP is 1, the state diagram draws FETCH, the state the edge will lead
   to, in a dashed box, and a note under the diagram says why. The table's arrow for that edge is
   not marked. After the edge the controller is in FETCH, and the dashed box is gone.
4. At the same edge the PC takes C4, `010`, so the next edge fetches the handler's first line.

## c2Task (a numbered list)

1. The starting text is Module 9's stop logic: every cause halts the machine, and TRAP is always
   0.
2. Change it into the trap logic (a sub-list):
   - An interrupt is let in when FETCHING and IE are 1 and WAITING is not 0. Its cause is `81` if
     WAITING's bit 0 is 1, else `82`.
   - Of two causes the machine can give at one edge, the lower number wins. Those pairs are a
     fetch's cause (`11` or `12`) with an interrupt, where the fetch's wins, and the timer with
     the door, where `81` wins.
   - TRAP is 1 when an instruction faults or an interrupt is let in, and NOHANDLER is 0. HALT is 1
     when an instruction faults or an interrupt is let in and NOHANDLER is 1, or at a `stop` while
     CHECKING.
   - GO is 0 when TRAP or HALT is 1.
3. There are 17 tests, one for each row of the trap logic's table: each cause on its own, the
   events, which cause wins, and no handler.
4. The last row gives the decoder's cause `21` and the memory's `31` together. The machine never
   gives that pair: the decoder's cause counts only in READ, the memory's only in MEMORY. The row
   checks that the logic still lets the lower number win, as the explanation's rule says.

## c2Hints.3 ("Part of the answer:", about 50 words)

1. `assign interrupt = FETCHING & IE & (WAITING != 2'b00);`
2. In the `always_comb`, the interrupt's lines go between the decoder's and the fetch's, so the
   fetch's still wins.
3. An interrupt never meets the decoder's or the memory's cause: it is let in only at an edge that
   would fetch. So where its lines go among those two does not change any row.

## reflection (about 70 words)

1. The machine can now trap: at one edge it puts the return point in C2 and the status in C1,
   goes to the handler in system mode, and later `resume` takes the program back.
2. Lessons 1 to 6 wrote handlers for these tasks: skipping refused stores, starting a program in
   user mode, the jobs of a system call, and the door and the timer.
3. Ask: can you write the handler that runs the shop's programs one after another, each in user
   mode, and offers them the jobs of lesson 4?
