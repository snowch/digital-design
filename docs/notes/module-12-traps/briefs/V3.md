# Brief V3: Module 12's figure and feedback words, after the reading review

Read `00-module.md` (the shared fact sheet) first, including its last section, "Decisions after
the reading review"; it applies here, with one change: these words appear on every Module 12 page,
so you may use **trap**, **handler**, **user mode**, **system mode**, **system call** and
**interrupt**, never bold. Each key is a short label or one or two sentences. A label has no full
stop; a sentence has one. Placeholders in braces, such as `{address}`, stay exactly as given: the
page puts a value there. Do not use backticks or other Markdown in these keys: they are plain text.

The page's words for a run, on Module 12's pages: "the program" is the user program only; "the
handler" is the code at the address C4 holds; "the start" is the lines from reset that set C4 and
start the program. A run ends at a `stop` the handler (or a program in system mode) runs, or when
the machine halts, or when the debugger cuts it off.

## How a run ended (the debugger's status line and the challenges' feedback)

- `stops.stop`: one sentence, after "Stopped" is no longer said: the run stopped at the stop at
  {address}. Do not say whose stop it was: on these pages it may be the handler's or the start's.
- `stops.cutOff`: one sentence: the debugger cut the run off after {n} instructions, because the
  run had not stopped. Module 11's form, for the shape: "The debugger cut the run off after {n}
  instructions: the program may never stop." Say "the run", not "the program".
- `stopsAt`: the trap timeline's line for the edge of a `stop`: {line}, at {address}: the run
  stops. ({line} is the line's text, such as stop.)

## The datapath figure (lesson 7 and Modules 8 and 9)

- `halted`: the status line when the machine has halted for a cause: Halted: {reason}. (The
  course's word for a cause ending the run is "halts"; "Stopped" is only for `stop`.)
- `haltsNext`: the status line before the edge that will halt: Halts at the next edge: {reason}.
- `reasons.22`: a short phrase after "Halted:": an instruction that user mode refuses.
- `reasons.32`: a short phrase: a device's address in user mode.
- `trapMove`: one sentence under the controller's state diagram, when the next edge traps: the
  next edge traps, so the controller goes to FETCH, whatever its table says for {state}.
- `heldMove`: one sentence under the diagram when the next edge halts or GO is 0 with no trap: GO
  is 0 and nothing traps, so the controller stays in {state}.

## The assembler

- `controlTransfer`: one or two sentences, after "Line N:", when a line uses a control register in
  a job, a load, a store or a branch: a control register is only copied to or from an R register,
  with a line of its own, such as R5 <= C2 or C2 <= R5. Then do the work in the R register.

## The challenge editor and the results cards

- `handlerLabel`: the heading over the text box where a Module 12 challenge's learner writes:
  Your start and handler.
- `failedLeft`: one sentence, the start of a failed test's feedback: The run left {left}.
- `emptyLeft`: one or two words in a sentence, where a check found nothing, such as no words
  shown or no causes: nothing.
- `leftCol`: a results card's column heading over what a run left: The run left.
- `runMatches`: one sentence on a card: The run left what the test asks.
- `runDiffers`: one sentence on a card: The run left something else.
- `checks.C2at`: the name of a check, in the middle of a sentence ("{name}: {value}"): C2, the
  return point, by the name of its line.

## Each challenge's sentence for how its runs must end (`ends.*`, after a failed test whose run
ended the wrong way; one or two sentences each; never give the answer's lines)

- `ends.skip34` (lesson 1): A run must stop at the program's end line, or at the handler's stop
  after a cause other than 34.
- `ends.saveRegisters` (lesson 2): A run must stop at the program's end line, with every refused
  store skipped.
- `ends.startUser` (lesson 3): A run must end at the handler's stop. The start must set C2 to
  program's address and C1 to the mode before resume.
- `ends.sensorService` (lesson 4): A run must end at the handler's stop for job 4, with no trap
  but the system calls.
- `ends.doorTimer` (lesson 5): A run must end at the handler's stop for job 4, after the program
  has shown 30.
- `ends.waitDoor` (lesson 6): A run must end at the handler's stop for job 4. Job 6 must put C1 and
  C2 back before its resume.
- `ends.shopHandler` (lesson 8): A run must end at the handler's stop after the last program, with
  a record for every program.

## Each challenge's sentence for what was wrong (`details.*`; one or two sentences; never give
the answer's lines). These replace the page's sentences.

- `details.saveRegisters` (lesson 2): The handler must count and skip each refused store, and
  leave every register, R0 to R15, as it was before the trap.
- `details.startUser` (lesson 3): The program must run in user mode. The handler must count and
  skip each cause 32, and save any other cause in the word at 408, then stop.
- `details.sensorService` (lesson 4): Job 2 must put the reading of the room in R2 into R1: room A
  for 0 and room B for 1. A system call may change only R1 and R2: the handler must put R8 and R9
  back before resume and leave every other register as it was.
- `details.doorTimer` (lesson 5): The timer's part must clear the timer's bit and, only if the door
  is still open, light ALARM beside the lamps already lit. It may change no register the program
  uses.
- `details.waitDoor` (lesson 6): Job 6 must let the door and the timer in while it counts, then
  give the program back its mode, its return point and every register but R1 and R2.
- `details.shopHandler` (lesson 8): The handler must run each program in the table in user mode,
  offer jobs 1 to 4, leave each program's record (0 for job 4, else its cause) at 400 plus 8 times
  its number, and stop after the last.
