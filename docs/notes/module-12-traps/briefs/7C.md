## explanation (about 170 words)

1. The trap logic chooses one cause when there are several. It takes the lowest number, in the
   order the steps run: the fetch's, then an interrupt, then the decoder's, then the memory's.
   This is Module 3's priority: the earliest step wins.
2. An interrupt is taken only at an edge that would fetch (FETCHING is 1), with IE at 1 and a bit
   of "waiting" set. The timer's `81` comes before the door's `82`.
3. With no handler, a cause halts the machine as Module 9's did. In system mode `stop` sets HALT
   too, and the program stops; in user mode `stop` is cause `22`.
4. The edge that traps writes the control registers, the PC and the controller's state at once,
   and nothing else: GO is 0, so no register, memory word or device changes.
5. A trap's edge does not count down the timer: no instruction finished. (The timer counts
   instructions, as lesson 5 said.)

## generalisation (about 110 words)

1. A trap adds no state to the controller. It ends the instruction where the cause appears and
   sends the controller to FETCH, so its cost is the edges the instruction had already taken.
2. The handler's address is a register, C4, not a fixed number in the circuit. The program
   chooses it.
3. Everything a handler sees, C0 to C4, is a register the circuit writes at one edge. The handler
   is ordinary instructions.
4. The trap logic is combinational: a table from its inputs to GO, TRAP, CAUSE and HALT.

## c2Task (numbered list)

1. The starting text is Module 9's stop logic: every cause halts the machine, and TRAP is always
   0.
2. Change it into the trap logic:
   - an interrupt when FETCHING and IE are 1 and WAITING is not 0, with cause `81` if WAITING's
     bit 0 is 1, else `82`;
   - the cause chosen in the order: the fetch's, the interrupt's, the decoder's, the memory's;
   - TRAP is 1 when anything traps and NOHANDLER is 0; HALT is 1 when anything traps and
     NOHANDLER is 1, or at a `stop` while CHECKING;
   - GO is 0 when anything traps or the machine halts.
3. There are 17 tests, one for each row of the table: each cause on its own, the events, which
   cause wins, and no handler.

## c2Hints (five, in this order)

1. The idea: a signal `interrupt` and a signal `traps` (any cause, or the interrupt), then TRAP,
   HALT and GO from those and NOHANDLER.
2. A common mistake: taking the interrupt whatever the state. It waits for an edge that would
   fetch.
3. A smaller example: Module 9's GO, `~(failed | stopNow)`, already says "not if anything stops
   the machine"; the trap logic's GO is the same with `traps` for `failed`.
4. Part of the answer: `assign interrupt = FETCHING & IE & (WAITING != 2'b00);`, and in the
   `always_comb`, the interrupt's lines go between the decoder's and the fetch's, so the fetch's
   still wins.
5. The whole answer:

```
  logic interrupt, traps;
  assign interrupt = FETCHING & IE & (WAITING != 2'b00);
  assign traps = failedF | interrupt | failedD | failedM;
  assign HALT = stopNow | (traps & NOHANDLER);
  assign TRAP = traps & ~NOHANDLER;
  assign GO = ~(traps | stopNow);
  always_comb begin
    CAUSE = CAUSEM;
    if (failedD) CAUSE = CAUSED;
    if (interrupt) begin
      if (WAITING[0]) CAUSE = 8'h81;
      else CAUSE = 8'h82;
    end
    if (failedF) CAUSE = CAUSEF;
  end
```

`assign stopNow`, up to `endmodule`.)

## modelVsReality (about 70 words)

1. Real machines add trap hardware in the same places: registers for the return point, the
   status and the cause, a choice of the next PC, and logic that picks one cause.
2. Machines that overlap instructions must also undo the work of the instructions after the one
   that faulted. This machine runs one instruction at a time, so it has nothing to undo.
3. This machine's priority, earliest step first, is its own choice.
