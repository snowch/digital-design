## explanation (about 130 words; a short table allowed)

1. The return point depends on the cause (a table, two columns):
   - a fault, causes `11` to `34`: the instruction that faulted, so the handler can mend it or skip
     it;
   - a system call, cause `41`: the instruction after the call, since the job is done.
2. So a handler first reads C3, and treats a system call differently from a fault.
3. The handler saves the registers it writes, as lesson 2 showed, and leaves the job's result in R1.
4. The figure runs the investigation's program in the debugger, with a breakpoint on the handler's
   first line.

## generalisation (about 110 words)

1. A system call looks like a function call: a number says which job, the words go in R1 to R4, and
   the result comes back in R1.
2. It differs in where the job runs. A call stays in the program's mode. A system call crosses into
   system mode at its trap's edge and back at `resume`'s edge.
3. The handler decides what each job may do. A user program reaches the shop's devices only
   through the jobs the handler offers.
4. A job the handler does not offer does nothing: the investigation's handler resumes without a
   word.

## c2Task (numbered list)

1. The starting text's handler offers job 1, show R2, and job 4, end the program. Add job 2: read a
   room's sensor. R2 is 0 for room A and 1 for room B, and the reading comes back in R1.
2. The handler must still put R8 and R9 back before `resume`.
3. There are 3 tests. Each adds a program after yours, named `program`, which reads rooms with job 2
   and shows words with job 1. Room A reads -184 and room B -250. Each test checks the words the
   display showed, in order, and that the run ends at a `stop`.

## c2Hints (five, in this order)

1. The idea: when R1 is 2, load the sensor R2 names into R1, then go to the handler's `back` line.
2. A common mistake: adding 4 to C2. A system call already returns to the next line.
3. A smaller example: job 1 is the one line `show: word[display] <= R2`, then the handler's `back`.
4. Part of the answer: `R8 <= 2` then `if R1 == R8 goto sensor`, beside the tests for jobs 1 and 4.
5. The whole answer: add these lines to the starting text, the first two after
   `if R1 == R8 goto end`, the rest before `end: stop`:

```
        R8 <= 2
        if R1 == R8 goto sensor
sensor: R1 <= word[sensorA]    // room A when R2 is 0
        R8 <= 0
        if R2 == R8 goto back
        R1 <= word[sensorB]     // room B otherwise
        goto back
```

## reflection (about 70 words; end on the question)

1. A user program asks, and the handler answers at the edge after the program's `call system`.
2. The shop's door does not ask. It opens when someone opens it, while whatever program runs.
3. The handler cannot wait for a program to make a system call before it lights ALARM.
4. End on the question: how can the machine go to the handler when the door opens, between two
   instructions of a program that knows nothing of the door?

## modelVsReality (about 60 words)

1. Real machines make system calls as this one does: one instruction, a number for the job, and the
   job's words in registers.
2. Real handlers offer hundreds of jobs, chosen from a table by the number. This handler compares
   the number with each job in turn.
3. The numbers 1 to 4 and their jobs are this course's own.
