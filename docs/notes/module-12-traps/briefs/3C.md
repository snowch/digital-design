## The memory map in user mode, as the figure gives it

The ROM (`000` to `3FF`): loads allowed; stores trap with cause `34`, as in system mode. The RAM
(`400` to `7BF`): every access allowed. Every device's word (`7C0` to `7F7`): every load and store
traps with cause `32`. The last word, `7F8`: cause `31`, no memory, as in system mode.

## explanation (about 130 words)

1. In user mode the machine refuses what would let a program reach past itself: the shop's
   devices, the control registers, `resume` and `stop`.
2. Without `resume` or a control-register job, a user program cannot set C0 back to system mode,
   or change C4.
3. Without `stop`, a user program cannot stop the machine: its `stop` traps, and the handler
   decides what happens next.
4. The handler is the only way back to system mode. A trap's edge sets C0 to `01`; the handler
   runs in system mode, and `resume` gives the program back the mode C1 holds.
5. The figure gives the memory map as user mode meets it.

## generalisation (about 110 words)

1. The rule has two parts: the machine checks the mode at every instruction, and only a trap can
   enter system mode.
2. So a program the shop did not write can run in user mode without being able to switch ALARM
   off, change the handler, or stop the machine.
3. The protection covers the devices and the control registers. It does not cover the RAM: a user
   program can change any word there, the handler's own words included.
4. The ROM is safe in both modes, since no store reaches it.

## c2Task (numbered list)

1. The starting text sets C4 and goes to `program` in system mode. Its handler only stops.
2. Change it so that `program` runs in user mode.
3. When the program traps, the handler keeps the cause, C3, in the word at `0x400`, then stops.
4. There are 4 tests. Each adds a program after yours, named `program`, which does one thing user
   mode refuses. Each test checks C1 after the trap, the word at `0x400`, that 1 trap went to the
   handler, and that the run ends at a `stop`.

## c2Hints (five, in this order)

1. The idea: write 0 to C1 and `program`'s address to C2, then run `resume`.
2. A common mistake: `goto program`. The program then runs in system mode, and nothing it does
   traps.
3. A smaller example: the investigation's handler start writes C1 and C2 with `R1 <= 0`,
   `C1 <= R1`, `R1 <= program`, `C2 <= R1`, then runs `resume`.
4. Part of the answer: the handler's first two lines are `R5 <= C3` and `word[0x400] <= R5`.
5. The whole answer:

```
        R1 <= handler
        C4 <= R1
        R1 <= 0
        C1 <= R1
        R1 <= program
        C2 <= R1
        resume
handler: R5 <= C3
        word[0x400] <= R5
        stop
```

## reflection (about 70 words; end on the question)

1. A user program cannot touch the display, the lamps or the sensors.
2. But the shop's programs are written to show readings and light lamps.
3. End on the question: how can a user program show a reading, if it may not touch the display?

## modelVsReality (about 60 words)

1. Real machines have a mode bit as this one does; some have more than two levels.
2. Real machines also protect parts of memory from user programs, with hardware that checks every
   address against a table the handler keeps. This machine protects only its devices.
3. On this machine a user program can still overwrite the handler's words in the RAM.
