## Job 5 as it should be

```
wait:   R8 <= word[0x400]       // the program's R8 and R9 back now:
        R9 <= word[0x408]       // a trap in the loop saves them again
        R1 <= C1
        word[0x410] <= R1       // save C1
        R1 <= C2
        word[0x418] <= R1       // save C2
        R1 <= 3
        C0 <= R1                // system mode, interrupts on
        R1 <= 0
pause:  R2 <= R2 - 1
        if R2 != R1 goto pause
        R1 <= 1
        C0 <= R1                // interrupts off again
        R1 <= word[0x410]
        C1 <= R1                // C1 and C2 back
        R1 <= word[0x418]
        C2 <= R1
        resume
```

Its run, the door opening once 60 instructions have run: the door's interrupt comes after 61
instructions, inside the wait; the timer's after 90; ALARM lights. The program shows 5 and 6 and
ends; the handler stops at `0EC`. 242 instructions, 6 traps. The word at `410` holds 2 (C1, `10`)
and the word at `418` holds `10C`.

## explanation (about 160 words; a short list allowed)

1. A trap inside the handler writes C1, C2 and C3 as any trap does. What the handler still needs
   from them, it keeps first.
2. A handler that lets interrupts in (list the four steps):
   - keeps C1 and C2 in two RAM words of its own;
   - writes 3 to C0;
   - writes 1 to C0 when it is done, so nothing can come in while it puts C1 and C2 back;
   - writes C1 and C2 back, then runs `resume`.
3. The registers the handler saves at its start, R8 and R9 at `400` and `408`, are saved again by
   the trap inside. So job 5 puts the program's R8 and R9 back before it lets interrupts in, and
   then uses only R1 and R2, which the calling convention lets a job change.
4. A fault in the handler has no fix of this kind: the handler must check what a program gives
   it, such as a room number, before it uses it.
5. The figure runs job 5 as it should be, with the words at `410` and `418` shown.

## generalisation (about 110 words)

1. A trap inside the handler is safe only if the handler kept, before letting it in, everything
   that trap writes over and the handler still needs: C1, C2, and any saved registers.
2. Interrupts off is the default in the handler because it is safe: an event waits, and its bit
   keeps it.
3. A long job that leaves interrupts off makes every event wait as long as the job. Letting them in
   costs the handler the saving.
4. Every handler line must not fault. The handler checks what a user program gives it.

## c2Hints (five, in this order)

1. The idea: keep C1 and C2 in the RAM, write 3 to C0, loop, write 1 to C0, write C1 and C2 back,
   then `resume`.
2. A common mistake: writing 3 to C0 and nothing else. The door's interrupt writes over C2, and the
   wait's `resume` goes back into its own loop.
3. A smaller example: lesson 2's handler saved R5 with `word[0x408] <= R5` before it changed R5.
   C2 is kept the same way, through a register: `R1 <= C2`, then `word[0x418] <= R1`.
4. Part of the answer: put the program's R8 and R9 back from `400` and `408` first, since a trap
   in the loop saves them there again, and count with R1 and R2 only.
5. The whole answer: job 5 as given above, from `wait:` to its `resume`.

## modelVsReality (about 70 words)

1. Real machines let a handler be interrupted in the same way: keep what the second trap writes
   over, then let it in.
2. Many push the return point and status on a stack kept for the handler, so a trap inside a trap
   inside a trap still finds its way back.
3. Many also let urgent events in while less urgent ones wait. This machine has one level: on or
   off.
