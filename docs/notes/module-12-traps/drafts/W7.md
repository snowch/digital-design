motivation: Each part sits in the datapath or the control unit. To see a part, press the block it sits in. A block opens to show the parts inside. Each block is drawn with its title, written in code form, such as `datapath-traps`. The list names the block to press for each part, by that title.

Four parts change for a trap:

- The control registers, C0 to C4, each with a selector that picks its next word. Press `datapath-traps`, then `control-registers`. The selector `returnPoint` picks C2's word at a trap. It picks the PC plus 4 when the cause's bit 6 is 1. Only cause `41`, a system call, has that bit set. Otherwise it picks the PC itself.
- The next PC, which takes C4 at a trap's edge, C2 at `resume`'s edge, and otherwise what Module 9 gave it. Press `datapath-traps`, then `next-trap`.
- The trap logic, in the control unit where the stop logic was. Press `control-unit-traps`, then `trap-logic`. It reads the three causes (CAUSEF, CAUSED and CAUSEM), STOP, CHECKING, FETCHING, the bits of "waiting", IE and NOHANDLER. IE is C0's bit 1. When it is 1, interrupts are on. NOHANDLER is 1 when C4 is 0, or when C4 holds the PC. It sets GO, TRAP, CAUSE and HALT.
- The controller, in the control unit. Press `control-unit-traps`, then `controller-traps`. `resume` and a control-register copy, such as `R5 <= C2`, now go from READ to WRITE, as a function call does. It has one more new rule, for an edge that traps.

The mode is C0's bit 0. It goes to two places. The decoder gives cause `22` in user mode for `resume`, the control-register copies and `stop`. The memory port's checks give cause `32` in user mode for a device's address.

Every part takes its word at the same edge: the last edge of the instruction that traps. The trap takes no edge of its own.

The drawings are large. On a phone, scroll inside a drawing, or use its overview to move about.

p1Explain: The controller goes to FETCH. At an edge that traps, its state register takes FETCH, whatever its table says, as it does at a reset.

The table's move from READ is to ALU. The trap overrides that move. The `call system` ends at its READ edge, which is its second edge.

Before that edge, while TRAP is 1, the state diagram draws FETCH, the state the edge will lead to, in a dashed box. A note under the diagram says why. The table's arrow for that edge is not marked. After the edge, the controller is in FETCH, and the dashed box is gone.

At the same edge, the PC takes C4, `010`. So the next edge fetches the handler's first line.

c2Task: 1. The starting text is Module 9's stop logic. Every cause halts the machine, and TRAP is always 0.
2. Change it into the trap logic:
- An interrupt is let in when FETCHING and IE are 1 and WAITING is not 0. Its cause is `81` if WAITING's bit 0 is 1, and `82` otherwise.
- Of two causes the machine can give at one edge, the lower number wins. Those pairs are a fetch's cause (`11` or `12`) with an interrupt, where the fetch's wins, and the timer with the door, where `81` wins.
- TRAP is 1 when an instruction faults or an interrupt is let in, and NOHANDLER is 0. HALT is 1 when an instruction faults or an interrupt is let in and NOHANDLER is 1, or at a `stop` while CHECKING.
- GO is 0 when TRAP or HALT is 1.
3. There are 17 tests, one for each row of the trap logic's table: each cause on its own, the events, which cause wins, and no handler.
4. The last row gives the decoder's cause `21` and the memory's `31` together. The machine never gives that pair. The decoder's cause counts only in READ, and the memory's only in MEMORY. The row checks that the logic still lets the lower number win, as the explanation's rule says.

c2Hints.3: Part of the answer: `assign interrupt = FETCHING & IE & (WAITING != 2'b00);`. In the `always_comb`, the interrupt's lines go between the decoder's and the fetch's, so the fetch's still wins. An interrupt never meets the decoder's or the memory's cause: it is let in only at an edge that would fetch. So where its lines go among those two does not change any row.

reflection: The machine can now trap. At one edge it puts the return point in C2 and the status before the trap in C1. It goes to the handler in system mode. Later, `resume` takes the program back.
