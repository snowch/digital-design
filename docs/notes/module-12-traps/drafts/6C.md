explanation: A trap inside the handler writes C1, C2 and C3, as any trap does. The handler keeps what it still needs from them first.

A handler that lets interrupts in takes four steps:

- keeps C1 and C2 in two RAM words of its own;
- writes 3 to C0;
- writes 1 to C0 when it is done, so nothing can come in while it puts C1 and C2 back;
- writes C1 and C2 back, then runs `resume`.

The handler saves R8 and R9 at its start, at `400` and `408`. A trap inside the handler saves them again. So job 5 puts the program's R8 and R9 back before it lets interrupts in. After that it uses only R1 and R2, which the calling convention lets a job change.

A fault in the handler has no fix of this kind. The handler must check what a program gives it, such as a room number, before it uses it.

generalisation: A trap inside the handler is safe only if the handler has kept, before it lets that trap in, everything the trap writes over and the handler still needs. That means C1, C2 and any saved registers.

Interrupts off is the default in the handler because it is safe. An event that comes in while they are off waits, and its bit stays set until a program clears it.

A long job that leaves interrupts off makes every event wait as long as the job. Letting interrupts in costs the handler the saving.

No handler line may fault. The handler checks what a user program gives it before it uses that value.

c2Hints.1: The idea: keep C1 and C2 in the RAM, write 3 to C0, loop, write 1 to C0, write C1 and C2 back, then `resume`.

c2Hints.2: A common mistake: writing 3 to C0 and nothing else. The door's interrupt writes over C2, and the wait's `resume` goes back into its own loop.

c2Hints.3: A smaller example: lesson 2's handler saved R5 with `word[0x408] <= R5` before it changed R5. C2 is kept the same way, through a register: `R1 <= C2`, then `word[0x418] <= R1`.

c2Hints.4: Part of the answer: put the program's R8 and R9 back from `400` and `408` first, since a trap in the loop saves them there again, and count with R1 and R2 only.

c2Hints.5: The whole answer: job 5, from `wait:` to its `resume`.

```
wait:   R8 <= word[0x400]       // the program's R8 and R9 back now:
        R9 <= word[0x408]       // a trap in the loop saves them again
        R1 <= C1
        word[0x410] <= R1       // save C1
        R1 <= C2
        word[0x418] <= R1       // save C2
        R1 <= 3
        C0 <= R1                // system mode, interrupts on
        R1 <= 0
pause:  R2 <= R2 - 1
        if R2 != R1 goto pause
        R1 <= 1
        C0 <= R1                // interrupts off again
        R1 <= word[0x410]
        C1 <= R1                // C1 and C2 back
        R1 <= word[0x418]
        C2 <= R1
        resume
```

modelVsReality: Real machines let a handler be interrupted in the same way: they keep what the second trap writes over, then let it in.

Many push the return point and status on a stack kept for the handler, so a trap inside a trap inside a trap still finds its way back.

Many also let urgent events in while less urgent ones wait. This machine has one level: on or off.
