The lesson's title, shown above everything: "How can one machine run two programs at once?"

## question (section prose, 110 to 150 words)

Facts, in this order:
1. Quote 12.8's generalisation's last three sentences ("What it does not do here is share the
   machine ... That is beyond this module.").
2. The shop wants the gap between its rooms on the display all day, from the gap program, which
   never ends, and the day's report made as well.
3. 12.8's runner runs programs one after another. The figure below runs it with a table of two,
   the gap program first and the report second.
4. The machine runs one instruction at a time. End with the question: how can one machine run two
   programs that both get on?
Do not use the word "kernel" here. Do not state the run's result (94, X): the figure shows it.

## runnerLead (above the figure, 40 to 70 words)

Instructions: press "Run to the end" and watch the lanes: one for the start, one for the handler,
one for each program. Then look at the records at `400` and `408`. Ask the reader which lane
stays empty. Do not answer.

## runnerAfter (shown once the run has ended, 50 to 80 words)

Facts: the run was cut off after 5,000 instructions. The gap program's lane and the handler's
alternate: each `call system` goes to the handler and back. The gap is shown 94 times. The report's
lane stays empty and both records are still X: the runner starts the next program only when one
ends, and the gap program never ends.

## motivation (section prose, 200 to 250 words)

Facts, in this order:
1. The program that runs the others is a **kernel**: the program the machine runs first, in system
   mode; it alone reaches the devices and the control registers, and it starts, stops and switches
   the other programs. Plain English first, then the term in bold. Here it is Module 12's start and
   handler, grown.
2. A user program reaches a device only through a system call. The figure above already showed
   one, again and again: the gap program's `call system` moves into the handler's lane; C2 takes
   the line after it, C3 takes `41`, the mode becomes system, the job runs, and `resume` goes back
   to the line after the call.
3. A system call happens only when the program asks. The gap program never asks to give up the
   machine.
4. The timer (12.5) interrupts a user program between two instructions without asking it. So a
   kernel can take the machine back from a program that never asks.
5. To give the machine to another program and later come back, the kernel must keep everything the
   machine holds for the stopped program. The kernel in this lesson keeps it in a save area of its
   own in the RAM, one for each program, and puts the other program's back.

## prediction (section prose, 60 to 90 words)

Facts: the figure runs the kernel with both programs and the timer set to 80. The third timer
interrupt stops the gap program before `R2 <= R5 - R1`, with R5 holding room A's reading, -184.
The report then runs, and it sets its own R5 to 0. Ask: when the gap program next runs
`R2 <= R5 - R1`, what will R5 hold? Tell the reader to choose and press "Check my prediction". Do
not answer and do not say "saved" or "put back".

## p1Question (one sentence)

Asks what R5 holds when the gap program next runs `R2 <= R5 - R1`.

## p1Explain (shown after the reader commits, 60 to 90 words)

Facts: R5 holds -184, room A's reading. The kernel saved all sixteen of the gap program's
registers in its save area before the report ran, and put them back before the gap program went
on. The gap program cannot tell it was stopped. One short clause for each wrong option: 0 is the
report's R5, which went into the report's save area; -250 is room B's reading, which the gap
program has not yet asked for; X would mean the register was never set.
