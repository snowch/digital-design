# Brief L3: the kernel chapter, explanation, generalisation, reflection and the model note

Read `docs/style.md`, then `docs/notes/beyond-the-machine/briefs/kernel-facts.md` (the fact sheet:
the voice, the banned words, the working words and every fact). Use only those facts. Do not write
or change any file. Return each item under its key (a heading line `## key`), as Markdown, with no
commentary. About 450 words in all.

Before this brief: the reader has watched the switch save one program's words and put back the
other's, worked out the words the switch stores at a moment of its own, and seen a count of 40 stop
both programs.

## explanation (section prose, 170 to 220 words)

Facts, in this order:
1. What a program is to the machine between two instructions: its sixteen registers, C2 (where it
   goes on) and C1 (its mode and whether interrupts are on). Everything else of it is in the ROM
   and the RAM and stays put.
2. So the switch saves those eighteen words and puts eighteen others back, and the stopped program
   cannot tell it was stopped.
3. Each program has its save area. The kernel keeps two addresses: the running program's at `480`
   and the waiting program's at `488`, which change places at each switch.
4. The kernel saves into its own words, never onto the program's stack (12.2), and saves every
   register, because an interrupt may change none (12.5).
5. A system call goes back to the program that asked; the timer's interrupt may go back into the
   other program.

## lanesLead (above the figure, 30 to 50 words)

The figure draws the kernel's run as lanes over its first switches: the start, the kernel's
handler, the gap program and the report, with the mode as a band and interrupts as a second band.
Instruction: press the figure's button to go move by move, and watch where each move goes.

## lanesAfter (shown once the figure has reached its end, 40 to 70 words)

Facts: the two programs' lanes alternate, always through the handler's. Each system call goes into
the handler and back to the program that asked. Each timer interrupt goes into the handler and out
into the other program. Each switch is 60 instructions in the handler's lane.

## generalisation (section prose, 120 to 160 words)

Facts:
1. One machine runs one instruction at a time. A person at the display sees both programs at work.
   Module 0's "A phone runs many programs at once" is a kernel switching quickly.
2. The cost here: 60 instructions of switching for every turn, against a program's 29 at a count of
   80.
3. Named, not taught, as a list: real kernels run many programs and choose which runs next; they
   give each program memory of its own that the others cannot reach (here the report could write
   over the gap program's save area, 12.3's unprotected RAM with more at stake); their timer counts
   time, not instructions; a program that waits for a device gives up the machine meanwhile.

## reflection (section prose, 110 to 150 words)

Facts:
1. The course began with a machine that runs one program, and ends with a kernel that runs two on
   it.
2. Two questions for the reader: what had to be saved, and why? What would the machine need to
   keep one program out of another's words?
3. One paragraph that points on, the only one on the page: the author's book *Systems From Scratch*
   follows a real kernel, xv6, a kernel written for teaching. Its chapter
   [Traps and System Calls](https://snowch.github.io/computer-systems/traps-and-system-calls/)
   follows one system call into xv6 and back out: the hardware records where the program was and
   why, turns interrupts off, changes the mode and jumps to the handler, as this machine's trap
   does, and the software saves every register, because one way in serves calls, faults and the
   timer. [Scheduling and Context Switches](https://snowch.github.io/computer-systems/scheduling-and-context-switches/)
   shows what xv6 saves when it switches programs, and why that switch saves fewer registers than
   the trap. Keep the two links exactly as given. Do not name any instruction of a real machine.

## modelVsReality (60 to 90 words)

Facts: this kernel runs two programs, both already in the ROM, in a fixed order. The timer counts
instructions, so every run is the same. The RAM is not protected, so a program could write over
the other's save area. A real kernel loads programs from storage, runs many, chooses which runs
next, gives each its own memory that the others cannot reach, and its timer counts time.
