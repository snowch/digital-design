The lesson's title, shown above everything: "Can a program write the instructions for a line you
write?"

## question (the Question section's prose, 120 to 160 words)

Facts, in this order:
1. Quote 11.1's generalisation: "The assembler translates line for word. It adds no instruction of
   its own: every word in the listing comes from one line you wrote."
2. Quote 13.2's: "Every program reaches a machine as machine code. Whatever language it was
   written in, the machine runs words like `A7345000`."
3. Module 0's shop wanted the display to show how much warmer room A is than room B. Its program
   took four lines for that (lines 1 to 4). The shop would say it in one line:
   `display <= sensorA - sensorB`.
4. End with the question: can a program take a line that says what to work out, and write the
   instructions that work it out?
Do not use the word "compiler" here.

## askedLead (above a figure, 40 to 70 words)

The figure below the question is the debugger from Module 11, holding two lines,
`display <= sensorA - sensorB` and `stop`, which you can edit. The assembler refuses line 1, with
its sentence "Each line is one instruction. Write it as a transfer, such as R3 <= R1 + R2." Tell
the reader to read the refusal, and to try writing line 1 as the assembler wants. Do not say how
many lines that takes.

## motivation (the Motivation section's prose, 180 to 230 words)

Facts, in this order:
1. Such a program is a **compiler**: a program that reads lines that say what to work out, and
   writes the instructions that work it out. Plain English first, then the term, in bold.
2. Set against the assembler, a list: the assembler makes one word for each line; the compiler
   writes several instructions for one line, chooses the registers, makes up a name for a line,
   and turns a comparison over.
3. The compiler's lines are the course's own text with the assembler's refusals lifted. Give the
   two forms: `D <= E`, where D is `display` or `lamps`; and `if E C E then D <= E`, where C is a
   comparison. An E is a device's name, a number, two of them joined by a job, or a piece in
   brackets. Jobs are done left to right, brackets first.
4. The one trap: in the compiler's lines a device's name stands for its word, the reading, while
   in assembly the name alone is its address: `R1 <= sensorA` assembles and puts `7D8` in R1.
5. The compiler is a program in the page, as the assembler is. It refuses a name that is no
   device, a number that does not fit, `*` and `/` (the machine has no multiplication or
   division), and a line in no form.

## prediction (the Prediction section's prose, 50 to 80 words)

The figure below compiles Module 0's CLASH rule as one line:
`if sensorA - sensorB >= 100 then lamps <= 4`. It is stopped after 4 instructions, with the line
now `if R3 >= R4 then lamps <= 4`. Say what has happened so far: the reading of each room went into
R1 and R2, the gap into R3, and 100 into R4. Say the next instruction the compiler writes deals
with the `if`. Do not say any rule about the branch: not "turned over", not "signed", not "past".
Tell the reader to choose and press "Check my prediction".

## p1Question (one sentence)

Asks which branch the compiler writes next.

## p1Explain (shown after the reader commits, 60 to 90 words)

Facts: the compiler writes `if R3 < R4 signed goto after1`. The branch jumps past `lamps <= 4`
when the comparison fails, so it tests the comparison turned over: `>=` turned over is `<`. The
readings can be of either sign, so the comparison is read signed. `after1` is a name the compiler
makes up for the line after the rest. Each wrong option, one short clause each: `>=` is the
comparison not turned over, so it would skip the lamps when the gap is 100 or more; `R4 < R3`
swaps the registers, which is `>`, wrong here; `unsigned` reads a negative gap as a huge number.
