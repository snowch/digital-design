explanation: The decoder works the same way Module 5 built next-state logic. Module 5 used Module 3's decoder to give one line per state, then AND gates for each row, then OR gates to build each bit of the next state.

Here, Module 3's decoders run on K, so one line goes high for each kind. An AND gate per kind and an OR gate per signal build the control signals from the kind lines. Where a signal follows the job, an AND gate joins the kind's line with the job bit first.

The decoder has no register. Its signals change as soon as K or J changes, and they settle before the next edge.

A load, a store and a jump use OP = `010` to add. A branch uses OP = `011` to subtract. For a load or a store, AZERO is J3 and BYTE is J0.

generalisation: These circuits generate control signals; together, they form the **control unit**. This design works for any list of kinds. Each kind gets one line; each control signal is an OR of the lines that need it.

Adding a kind adds one line and joins it to the OR of every signal that kind needs. No other kind's signals change.

Kinds 0 and 9 to F have no line, so every signal is 0 for them.

Gates suffice because Module 8's machine runs each instruction in one edge. A machine that takes several edges needs signals that change from edge to edge. Lesson 3 adds them.

modelVsReality: Real design tools simplify the gates. They share terms between signals and drop gates that change nothing.

The course keeps one OR per signal, so each gate matches a row of the table. Both give the same control signals.

In the model the decoder settles in a few steps of the settle model. A real decoder's gates take time, and that time adds to each instruction's path from the fetch to the register write.
