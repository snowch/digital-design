# Brief 3C: lesson `several-edges` (Module 9, lesson 3), explanation to the end

Read `00-module.md` (the shared fact sheet) first; it applies here. "control unit", "illegal
instruction" and "instruction register" are allowed. "micro-operation" must not appear.

Keys to write: `explanation`, `controllerLead`, `controllerAfter`, `generalisation`,
`kindEdgesLead`, `kindEdgesAfter`, `writeStatesLead`, `c2Task`, `c2Hints.1` to `c2Hints.5`,
`reflection`, `modelVsReality`.

## explanation (above the controller's figure; about 140 words, a list allowed)

1. The control unit is now the block "digits", the decoder, the controller and the stop logic.
2. The controller is Module 5's state machine: a 3-bit register holds the state's code, and
   next-state logic works out the next code. The codes are FETCH `000`, READ `001`, ALU `010`,
   MEMORY `011`, WRITE `100`.
3. The next state depends on three of the decoder's signals: CALL, MEM (a load or a store) and
   WRITEY.
4. The PC keeps the instruction's address until its last edge, for three reasons:
   - a call's WRITE edge writes PC + 4 into register Y;
   - a branch's target is PC + 4c;
   - a stop leaves the PC on the stop, as Module 8's machine did.
5. The decoder's checks count only in READ. In FETCH, IR still holds the last instruction, or 0
   after a reset, and 0 is illegal.
6. The fetch's checks count only in FETCH. In other states the address is HR, a data address.

## controllerLead (above the state machine's figure; about 60 words)

1. The figure is the controller as Module 5 drew state machines: its state diagram, its table of
   rows, and a trace.
2. Set CALL, MEM and WRITEY as a kind sets them, then press "Clock CLK" to move to the next
   state. A load sets MEM and WRITEY to 1 and CALL to 0.

## controllerAfter (below the figure; about 100 words, a list allowed)

1. FETCH always leads to READ, and WRITE always leads to FETCH.
2. From READ, a call goes to WRITE. Every other kind goes to ALU.
3. From ALU, a load or a store (MEM 1) goes to MEMORY. A kind that writes register Y goes to
   WRITE. A branch or a jump goes back to FETCH.
4. From MEMORY, a load goes to WRITE, and a store goes to FETCH.
5. An edge whose next state is FETCH is the instruction's last edge.

## generalisation (about 90 words)

1. Each kind takes as many edges as it has work for, no more.
2. A call needs no ALU edge. Its target, PC + 4c, comes from the next-PC adder, and PC + 4 is
   written into register Y.
3. A branch and a jump end at the ALU edge: the ALU's result decides, or is, the next PC.
4. A program's edges depend on its mix of kinds.
5. Each edge does less than Module 8's one edge did: one register read, one ALU job, or one
   memory access.

## kindEdgesLead (above the table figure; one or two sentences)

1. The table is read off the decoder and the controller: each kind's signals are given to the
   controller, and its states are counted until it is back at FETCH.

## kindEdgesAfter (below the table; about 50 words)

1. A register job and a constant job take 4 edges: FETCH, READ, ALU, WRITE.
2. A load takes 5. A store takes 4: it ends at MEMORY.
3. A branch and a jump take 3: FETCH, READ, ALU.
4. A call takes 3: FETCH, READ, WRITE.

Write the controller's next-state logic.

## c2Task (about 130 words)

1. The module `controller` has inputs CLK, RST, GO, CALL, MEM and WRITEY, and output S, the
   state's 3-bit code.
2. The text names the states with `typedef enum`, as Module 5 did. The state register is
   written: at an edge it takes FETCH if RST is 1, otherwise `next` if GO is 1. GO is 0 once the
   machine halts.
3. The start sends every kind through FETCH, READ, ALU and WRITE. MEMORY is never used.
4. Rewrite the `always_comb` so each kind passes through its own states, as the table above
   gives them.
5. The tests take a register job, a load, a store, a branch and a call through their states
   from a reset, then a stop that halts in READ. One test drops GO while CLK is 1. 44 tests.

## c2Hints (five rungs; the fifth gives the whole answer)

1. FETCH's and WRITE's arms read no input. READ reads CALL. ALU reads MEM, then WRITEY. MEMORY
   reads WRITEY.
2. A common mistake: in ALU, testing WRITEY before MEM. A load has both at 1, and it must go to
   MEMORY first.
3. READ's arm: `READ: begin if (CALL) next = WRITE; else next = ALU; end`
4. MEMORY's arm: `MEMORY: begin if (WRITEY) next = WRITE; else next = FETCH; end`
5. The whole `always_comb`:

   ```
   always_comb begin
     case (state)
       FETCH: next = READ;
       READ: begin
         if (CALL) next = WRITE;
         else next = ALU;
       end
       ALU: begin
         if (MEM) next = MEMORY;
         else if (WRITEY) next = WRITE;
         else next = FETCH;
       end
       MEMORY: begin
         if (WRITEY) next = WRITE;
         else next = FETCH;
       end
       default: next = FETCH;
     endcase
   end
   ```

## reflection (about 80 words)

1. One memory port serves the fetch and the data, at different edges.
2. The instruction register keeps the instruction, and HA, HB, HR and HM keep the words that
   pass from one edge to the next.
3. The controller's state says which edge the instruction is at.
4. End on the question: which control signals make each edge do its work, and how does the
   controller set them?

## modelVsReality (about 90 words)

1. A clock's edges must leave time for the slowest path from one register to the next.
2. In Module 8's machine one edge held a load's whole path: the fetch, the decoder, the register
   file, the ALU, the memory and back to the register file.
3. Here each edge holds one part of it, so a real clock could run faster.
4. Whether the program then takes less time depends on how the parts' times compare. Real
   designers split the work so the edges' paths take about the same time.
5. The course's settle model counts steps, not time.
