I reviewed lesson 9.4 (micro-operations), reading as a learner who has done 6.1 to 9.3. I checked facts against `docs/isa.md`, `DatapathFigure.tsx`, `content/lessons/micro-operations.facts.test.ts` and `state-machines.prose.ts`. I wrote no files.

## Findings, ranked by harm to a learner

**1. The new term's first worked example miscounts it (motivation).** The lesson says "One such transfer is a **micro-operation**". It then says "R3 ← R1 - R2 in Module 8 becomes four micro-operations", but the list holds six transfers: IR, HA, HB, HR, R3 and PC. By the lesson's own definition that is six micro-operations, or four edges. A learner meets the term for the first time and immediately finds it counted two ways. Direction: make the count match the definition (count edges, or count transfers), and keep it that way through the rest of the page.

**2. The investigation's closing claim is contradicted a few lines earlier (figure four-views, "After").** "Every control signal that makes a register write is 1 only in its own state." The same paragraph block has just shown PCEN at 1 in WRITE (for the load) and in ALU (for the branch). The construction also defines PCEN by the instruction's last edge, not by one state. Direction: limit the claim to the signals it is true of, or say how PCEN differs.

**3. The "After" text cites values the figure does not show (four-views).** It says "AZERO and BCONST are both 1" and "HR takes `7D8`", and that HM reads the word. But the figure's `signals` list has only FETCHING to PCEN and GO, so no AZERO or BCONST. It also has no `buses`, so no table shows HR or HM; the drawing does not write wide buses. The lead also says the signals view gives "the value of every control signal", which overclaims for the same reason. The learner is asked to read things the views do not give. I could not confirm whether opening a block shows these values. Direction: add the named signals and buses to the figure, or rewrite the "After" text to use only what is shown.

**4. "Each signal is the state AND the kind AND GO" is stated three times, and the lesson's own list breaks it.** The construction opens with "Each control signal combines three things: the machine's state, the instruction's kind, and GO". The generalisation says "Each control signal is built the same way: the state's line, AND what the kind needs, AND GO", and the reflection repeats it. The construction's own list breaks the rule:
- FETCHING and CHECKING read neither the kind nor GO.
- MLOAD and MSTORE do not read GO.
- IREN, HOLDAB and HOLDR do not read the kind.
- PCEN is not one state's line.

The construction's second paragraph even says why. A learner who trusts the summary will make exactly the mistake that hint 2 of controller-text warns about (ANDing GO into CHECKING). Direction: state the rule as covering the signals that make a register take a word, and say it once.

**5. The explanation keeps half of Module 5's argument and drops the half that no longer holds.** Module 5 said the output logic "reads the state alone. An input that changes between edges cannot change them; only an edge can" (`state-machines.prose.ts`). Here the lesson explains why the decoder's signals are steady, because IR changes only at a fetch. It never says that GO can change between edges. Yet controller-text tests exactly that ("GO falls while the clock is high"), and hint 2 relies on it. Direction: say that GO is the one input that can change mid-edge, and what that does to the outputs that read it.

**6. The second challenge repeats the first (construction and challenge).** controller-text gives the next-state logic already written. Its reference is outputs-text's answer with `S == 3'bxxx` swapped for `state == NAME`, and ENDS swapped for `next == FETCH`. A learner who did the first challenge copies it across. The only new idea, PCEN from `next`, is given away in the task text ("compare `next` with FETCH") and in hint 4. Direction: either give the second challenge work of its own, or make PCEN-from-`next` the task without stating it in the task text.

**7. The failure outcome contradicts itself (signal-faults, MSTORE stuck at 0).** "Every edge runs as it should" is followed by "At the store's MEMORY edge, the only micro-operation is PC ← PC + 4". Direction: say what stays the same (the sequence of states and the 18 edges) instead of "runs as it should". The facts test confirms 18 edges, R3 at 66 and the display at 0.

**8. The generalisation contradicts itself on hardware.** "A new kind needs no new hardware if its micro-operations are ones the machine already makes. It needs a list of states and a column of signals in the decoder." A decoder column is gates, and a new path through the states changes the next-state logic. This also front-runs 9.5, whose question asks "How much of the machine must change". Direction: name what does not need to change (the datapath) and leave the rest to 9.5.

**9. "The margin program from Module 8" is not Module 8's program (prediction and signal-faults leads).** Module 8.3's margin program ends `R4 ← R3 + R3`, `stop`, with no display. This one stores R3 to the display. Lesson 9.3 has the same wording, so it is inherited. A learner who remembers 8.3 will notice the change. Direction: say it is a version that shows the result on the display.

**10. Smaller wording and style points:**
- **Prediction:** "a constant job whose job is copy B" uses "job" in two senses in one phrase.
- **Motivation:** "A register writes a word only if its enable signal is 1" should say the register *takes* a word; elsewhere the page says a register is written.
- **four-views lead:** it announces "four linked views" and then adds a state diagram and a timing diagram, which makes six things. The generalisation later repeats "The four views read the same simulator…".
- **Explanation:** one paragraph carries five ideas (Module 5 contrast, IR stability, settling, the edge, PCEN), against style rule 2. It also says "PCEN uses the next-state logic" just after the learner built PCEN from the state code, without saying the two give the same signal.
- **Reflection:** "the routine called" uses *routine*, which no earlier lesson introduces.
- **controller-text:** the task says "The test suite has 35 tests", but 38 test labels are listed. `micro-operations.facts.test.ts` pins `testCount` at 35, so the extra 3 are probably steps with no check, as in 9.3. If the page lists all 38 rows, the learner sees a mismatch. I could not check what the page shows.

## What works

The prediction is well chosen. It is checked by the simulator, and its answer turns on HR, not on the register the learner expects. The PCEN-stuck-at-1 experiment makes the PC's single write per instruction concrete, with an edge-by-edge account that the facts test pins. The lesson links back cleanly from 9.3's closing question to its own.
