Sceptic verdicts on the 9.5 (new-instruction) review. I wrote no files.

**1. CALL and JUMP renamed without a word: Stands.** 9.1 line 41 says "kind 6's CALL, kind 7's JUMP", and 9.1 line 95 says "Adding a kind adds one line and joins it to the OR of every signal that kind needs." The 9.5 fault lead (prose.ts:39) uses "orCall" and "orJump" and "kind 6's line" before the explanation says "Kind 6's line is KIND6 … CALL and JUMP are OR gates." Smallest fix: before the fault lab, say in one or two sentences that adding kind 9 gives CALL and JUMP an OR gate each, so the kind 6 and kind 7 lines become KIND6 and KIND7. The construction is the natural place. The explanation then only needs to point back to it.

**2. "Chooses at run time" is not shown: Stands.** The program's first line is `R4 <= showA`, a constant, and the only alternative offered is "With R4 ← `018` instead", which is an edit to the program. 9.4's closing line makes the same claim ("chosen while the program runs"). Smallest fix: soften the motivation and the figure lead to what the figure shows (the target comes from a register, so any value the program puts there picks the routine). Changing the program is the bigger option.

**3. "Kinds A to F stay free in the course's machine": Stands.** The page's own Model versus reality says "The course's machine still refuses kind 9", and docs/isa.md line 255 says "Kinds 9 to F are free for them." Fix: say "your copy" in that sentence, or say 9 to F for the course's machine.

**4. Reflection summary: Partly.**
- "3 to 5" is wrong: 9.3 line 46 says "The stop takes 2 edges". Fix the range.
- "Two machines now run the same instructions" sits uneasily next to a kind 9 that only the learner's copy has. Qualify it.
- "Both leave the same registers and memory after every instruction" is the weakest of the three, but it is a claim, not an error. No earlier lesson states it outright, though 9.3 runs the same program on both machines. Hedge it or drop it.

**5. "It needs no ALU edge. The ALU is gates." gives the wrong cause: Falls.** The review says the learner "meets the wrong cause first", but the page puts the cause first: "The decoder sets CALL, so the controller moves from READ to WRITE." comes before "It needs no ALU edge." The "ALU is gates" sentences then explain why skipping ALU is safe (the result is ready by WRITE). That is a separate, correct point. The jump line that follows supports it.

**6. Repetition: Partly.** These stand:
- "a column in the decoder and two changes to its checks" appears in the explanation (line 117), the generalisation ("This one needed only the first two") and the reflection (line 149), after the construction's bullets already said it. CLAUDE.md lists "the same argument made twice" as a defect. Keep it in one place, probably the generalisation, and cut the explanation's opening line and the reflection's restatement.
- The question section asks its question twice ("Which parts of the machine would have to change?" and then "How much of the machine must change…"). Keep one.

The new-edges lead naming FETCH, READ, WRITE again Falls: a figure lead says what its table shows, and here the call and jump sequences sit side by side for comparison.

**7. Machine-text hint 2, "sending kind 9 through ALU in the controller": Stands.** The controller in the starting text reads only CALL, MEM, WRITEY, LOAD and STORE, never the kind, and hint 1 says "Only the decoder module changes." The mistake can't be made as described. Fix: describe it as the decoder signal that sends the controller from READ to ALU being left at 0. That stays short of the arm itself, which hint 3 gives anyway.

**8. Reset during the call: Partly.**
- The first point is weak but cheap to fix. 9.3's controller task does the same ("One test drops GO while CLK is 1") with no reason given, so a learner has met the pattern. Here the learner edits only the decoder, though, so "a reset rises and falls while CLK is 1" can read as something they must do. Add a few words saying that this checks a reset acts only at an edge.
- The second point Falls. The panel shows "All {total} tests pass", and `book.tsx:142` computes total as `steps.filter((s) => s.expect).length`, which is 23 here (pinned in new-instruction.facts.test.ts:82). The 46 labels appear only in the text dump. 9.3 follows the same convention (46 labels, "There are 44 tests").

**9. "kind 9 with constant `008`": Partly.** It is true that nothing says why. But the reviewer's guess is wrong. The decoder suite compares output signals (DECODER_VECTORS, new-instruction.ts:72-89), and BCONST is already checked directly by "K 9, J 0" at constant 0. So the 008 case doesn't exist to expose a missing BCONST. It checks that kind 9 is accepted with a non-zero constant, i.e. that no constant check (like kind 8's) refuses it. If anything is added, tie it to that, in a few words.

**10. Smaller points: Falls on all three.**
- **(a) "the machine's text … `if (JUMP) NEXT = RESULT;`".** The learner wrote that exact line in 8.5's datapath challenge (8.5 lines 228, 236, 244: "`if (JUMP) NEXT = RESULT;` is the jump's case."). It is familiar text, not unseen text.
- **(b) "free" never introduced.** 9.2's Model versus reality says "Real makers keep some kinds reserved, as this machine keeps kinds 9 to F, so a later version can define them." The learner has been told.
- **(c) "state" in two senses.** It is one sense. "its states" means the controller's states. "check the state and the PC after every edge" also means the controller's state: the tests expect `S` (new-instruction.ts:144, `expect: { S: code(next), PC: … }`). No clash.
